17

学習ロードマップ

「どの順番で身につけるか」。各ステップに到達目標（できるようになること）を置いています。

原理との対応

この章は原理の実装ではなく、3-9 の原理を身につける順番です。1 日目は 3-9 ガードレール（止められる・巻き戻せる）と 3-9 コンテキスト（コンテキストを見る）、1 週目は 3-9 メモリ（外に残す・分ける）と 3-9 ループ（合否をループに入れる型）、2〜4 週目は図 1-1（1-1）の「拡張とオーケストレーション」を「コンテキストに足すのか、ハーネスで実行するのか」で選び、1〜3 か月で 3-9 のガードレールの「ハーネスで強制する」側と図 1-1 の「運用と観測性」に進みます。各節末の「到達判定」は、操作を覚えたかではなく原理で説明できるかで判定します。廃れないのは順序の根拠（認知負荷が小さく、効き目が早い順）と判定の観点で、変わるのは各行のコマンド名と参照先です。

17-1. 基礎（1 日目）

やること到達目標参照
インストールしてプロジェクトで claude を起動対話セッションを開始できるクイックスタート
コードベースに質問する探索的な使い方を体験する一般的なワークフロー
/init で CLAUDE.md を生成プロジェクト規約を持たせるメモリ
Shift+Tab で権限モードを切り替えるPlan / acceptEdits の違いを理解する権限モード
Esc・/rewind・/clear を試す失敗を巻き戻せる安心感を得るチェックポイント
到達判定

次の 3 つができれば 17-2 へ進んでください。(1) /rewind で戻せるもの（ハーネスが編集したファイル）と戻せないもの（コマンドが外部に起こした副作用）の違いを、3-9 ガードレール の「巻き戻せるのはハーネスが自分で触ったものだけ」で説明できる。(2) Shift+Tab の権限モードが「ツール実行の直前で止める」操作であることを、モデルは選ぶだけで実行しないという 3-9 ツール使用 の往復で説明できる。(3) /init で生成した CLAUDE.md が「毎セッション先頭に足されるコンテキスト」であって強制ではないことを、3-9 メモリ の言い方で言える。

17-2. 日常運用（1 週目）

やること到達目標参照
CLAUDE.md を実務に合わせて育てる同じ指摘を 2 回したら追記する習慣がつく4-3
/permissions で安全なコマンドを許可プロンプト疲れが減る15-3
/context で内訳を見る何がウィンドウを埋めているか説明できる3-6
プランモード → 実装 → /code-review手戻りを減らす型が身につく5-3
調査を明示的にサブエージェントへ委譲本体のコンテキストを汚さずに調べられる11-1
/doctor で点検設定の問題を自力で切り分けられる15-1
このステップの完了確認 
/doctor     # 設定・依存・権限の点検結果が一覧で出る/context    # 固定分と会話の内訳、残量が出る

両方の出力を読んで「何が入っていて、何が問題か」を自分の言葉で説明できれば合格です。

到達判定

上の完了確認に加えて、次の 3 つができれば 17-3 へ進んでください。(1) /context の内訳を 3-9 コンテキスト の 7 項目（システム指示・CLAUDE.md・自動メモリ・スキル・会話履歴・読んだファイル・コマンド出力）に当てはめ、どれが「毎ターン送られる固定費」かを説明できる。(2) サブエージェントに委譲した調査で要約だけが戻り、過程が本体に残らない理由を 3-9 メモリ の「分ける」で説明できる。(3) /permissions で許可したルールと CLAUDE.md に書いた指示が、3-9 ガードレール の「ハーネスで強制する」と「文脈で頼む」のどちらに当たるかを自分で仕分けできる。

17-3. 拡張（2〜4 週目）

何をいつ足すかの判断基準は 9-3 にまとめてあります。

やること到達目標参照
繰り返す手順を Skill 化手順を /名前 で呼び出せる10-2
整形・Lint・通知を Hook へ「お願い」を「強制」に変えられる12-4
外部サービスを MCP で接続CLI で届かない先に手が伸びる13-2
専門役の Subagent を定義レビュアー・調査役を使い分けられる11-2
コードインテリジェンスを導入ファイル全読みが定義ジャンプに置き換わる14-3
.claude/rules/ に分割常時ロードを減らせる4-4
到達判定

次の 3 つができれば 17-4 へ進んでください。(1) 自分が足した Skill・Hook・MCP・Subagent のそれぞれが 3-9 のどの原理に属するか（Skill＝メモリの「外に残す」、Subagent＝メモリの「分ける」、Hook＝ガードレールの「ハーネスで強制する」、MCP＝ツール使用）を、図 1-1（1-1）の「拡張とオーケストレーション」の並びで言える。(2) Hook に移した処理（整形・Lint）と CLAUDE.md に書いたままの指示の違いを、3-9 ガードレール の決定論／確率で説明でき、「必ず守らせたいもの」を自分で Hook 側に置ける。(3) MCP サーバーを足したあとの /context の増分を 3-9 ツール使用 の「ツールの定義はコンテキストに入る」で説明でき、必要なら自分で減らせる。

17-4. チーム展開と自動化（1〜3 か月）

やること到達目標参照
設定・スキル・サブエージェントをリポジトリにコミットチーム全員が同じ土台で動く15-1
Plugin ＋ マーケットプレイスにまとめる複数リポジトリに配布できる14-3
CI に claude -p / GitHub Actions を組み込む人手を介さず回る16-2
定期タスクで PR レビュー・依存監査を自動化定型作業が手から離れる16-3
管理設定と管理 CLAUDE.md を分けて設計組織ポリシーを強制できる15-7
OpenTelemetry / 分析ダッシュボード利用状況とコストが見える7-5
Agent SDK で独自エージェント同じハーネスを自分のプログラムから使える16-4
継続的なキャッチアップ

公式ドキュメントの What's new（週次ダイジェスト） と changelog を定期的に確認するのが、最も確実な最新化の手段です。セッション内では /release-notes でも確認できます。

到達判定

次の 3 つができれば、このロードマップは完了です。(1) 組織ルールを管理設定と管理 CLAUDE.md のどちらに置くかを、3-9 ガードレール の「ハーネスで強制する」と「文脈で頼む」の区別で自分で判断できる。(2) claude -p を --bare と --allowedTools 付きで CI から動かし、テストや Lint の合否が周回ごとにコンテキストへ入る設計——3-9 ループ の「収束する条件」——を自分で組める。(3) Agent SDK の tools 定義が 3-9 ツール使用 のツール使用そのもの（定義はコンテキストに入り、モデルは選ぶだけで、実行は自分のコード側で起きる）であることを説明できる。

17-5. この章の持ち帰り

ロードマップの価値は「次に何をやるか」が常に 1 つに決まることです。

覚えること仕事での効き目具体的な操作
原理 → 操作の順で身につける3-9 の原理を先に持っていれば、各ステップの到達判定を自分で作れる。コマンド名や参照先が変わっても、判定の観点（何を触っているか・強制か依頼か・合否が入るか）は変わらない3-9 の 6 項・図 1-1（1-1）の全体像
1 日目は 5 つだけインストール → 質問 → /init → Shift+Tab → /rewind。ここまでで「戻せる」安心感が得られる巻き戻せると分かると任せる量が増える
1 週目の合格ラインは説明できること/doctor と /context の出力を自分の言葉で説明できれば、以降は自力で切り分けられる/doctor / /context
拡張は症状ドリブンで足す「学ぶべき機能」ではなく「今困っていること」から選ぶので、使わない設定が増えない9-3 のトリガー表
チーム展開は強制と指針を分けて設計管理設定＝クライアントが強制／管理 CLAUDE.md＝あくまで指示。混ぜると効かない17-4
追いかけ方を決めておく仕様変更が速い。定点観測の場所を 1 つ決めておけば陳腐化しないWhat's new と /release-notes
意外と知られていない

セッションを離れずに更新履歴を読めます。/release-notes は意外と知られていないコマンドで、「先週まで無かった挙動」に出くわしたときの初手として有効です。週次ダイジェストの What's new と合わせて、月 1 回眺めるだけでも、この資料のような二次情報だけを追うより確実に最新化できます。
