ガードレール機能

モデルは「実行したい」と言うだけで、外界に触れるのはハーネスだけです。だから止められる場所はツール実行の直前の 1 か所に集まります。権限モード・権限ルール・サンドボックス・フック・組織の管理設定は、すべてその 1 か所に置く強制の書き方で、違うのは「何を、どの粒度で、誰が決めるか」だけです。

原理との対応

この章は図 1-1 のガードレールの実装で、根拠は 3-6 ガードレール（副作用はハーネスにしかない）と 3-6 ツール使用（モデルは選ぶだけで、実行しない）です。CLAUDE.md やスキルは「文脈で頼む」側で、モデルが読んで従うことが多いだけで保証はありません。この章の手段はモデルを通さず、ハーネスがループの決まった位置で必ず動かすので決定論的に効きます。廃れないのは「守らせたい規則はコンテキストではなくハーネスに置く」「実行直前で止める」という分業で、変わるのはモードの既定値、ルール構文、イベント名の一覧、保護パスの一覧です。

5-1. ガードレールの全体像

手段は 5 つあり、同じ「ツール実行の直前」に、違う粒度で効きます。上ほど広く、下ほど細かい制御です。

手段何を決めるか粒度誰が決めるか本章
組織の管理設定下の 4 つの既定値と上限。個人やプロジェクトでは上書きできない組織・マシン全体IT 管理者5-8
権限モード確認ダイアログの頻度のベースライン（読むだけ／編集も／すべて）セッション全体利用者（Shift+Tab）5-2
権限ルールツール名と引数のパターンごとに、許可・確認・拒否ツール × 引数利用者・チーム（設定ファイル）5-4
サンドボックスBash がファイルシステムとネットワークのどこに触れるかOS レベルの境界利用者・チーム5-5
フック決まったイベントで自分のプログラムを必ず走らせる。ブロック・整形・通知・監査イベント × 任意の条件利用者・チーム5-6 / 5-7

どれを使うか

  • 「確認が多すぎる／少なすぎる」→ 権限モードを変える。日常は acceptEdits
  • 「このコマンドは毎回許可したい／絶対に通したくない」→ 権限ルールの allow / deny
  • 「確認を減らしたいが、勝手に外に出てほしくない」→ サンドボックス
  • 「編集のたびに整形したい」「特定条件で止めたい」「終わったら通知したい」→ フック
  • 「チーム全員に強制したい」→ 管理設定。行動指針の共有なら管理 CLAUDE.md（強制ではない）
CLAUDE.md との切り分け

CLAUDE.md に「.env を触るな」と書くのは依頼、権限ルールで Read(./.env) を deny するのは強制です。守られなければ困る規則はこの章の手段へ、守られると嬉しい程度の指針は 2 章 の手段へ。置き場所はこれで一意に決まります。

5-2. 権限モード

Shift+Tab が巡回するのは default（Manual）→ acceptEdits → plan の 3 つです。auto はアカウントが利用条件を満たすときだけ、bypassPermissions は有効化フラグ付きで起動したときだけサイクルに加わり、dontAsk は --permission-mode dontAsk でのみ設定します。モードは「ベースライン」で、この上に個別の許可／確認／拒否ルール（5-4）を重ねます。

モード確認なしで実行されるもの最適な用途
bypassPermissionsすべて（チェックなし）⚠ 隔離コンテナ・VM のみ
autoすべて。ただしバックグラウンドの安全チェック（分類器）付き長時間の自律タスク。Pro / Max / Team ではターミナル・VS Code の既定の開始モード（v2.1.228 以降）。claude -p・Enterprise・API キー等は default のまま。設定で変えるならユーザー設定の defaultMode（プロジェクト設定の auto は無視される）
dontAsk事前承認済みツールのみ。それ以外は確認せず拒否ロックダウンしたスクリプト
acceptEdits読み取り＋ファイル編集＋一般的な FS コマンド（mkdir/mv/cp 等）レビューしながらの反復開発。日常の現実的な選択
default（UI 表記：Manual）読み取りのみ導入初期、機密性の高い作業
plan読み取りのみ（編集せず計画を提案）変更前の調査・設計
  • bypassPermissions 以外では、保護されたパス（リポジトリ状態や Claude 自身の設定。5-5）への書き込みは自動承認されません
  • 拒否ルール・確認ルールは bypassPermissions を含むすべてのモードで有効です
  • 既定モードは設定の permissions.defaultMode で固定できます
最初に決めておくこと

bypassPermissions と --dangerously-skip-permissions は、Claude が確認なしにあらゆるコマンドを実行できる状態です（rm も git push も通ります）。ローカルの実プロジェクトでは使わず、使うなら dev container・VM・クラウドセッションなどの隔離環境に限定してください。日常は acceptEdits、確認を減らしたいときは安全チェック付きの auto が現実的な選択です。

試してみる：Plan Mode で起動 
claude --permission-mode plan

起動したら、そのまま次のように依頼します（このモードではソースは編集されません）。

5-3. 設定のスコープと優先順位

権限ルール・フック・サンドボックスはすべて設定ファイルに書きます。どこに書くかが「誰に効くか」と「誰の設定が勝つか」を決めます。

スコープ場所影響範囲共有
Managedサーバー管理設定 / plist / レジストリ / managed-settings.json組織またはマシンの全ユーザーIT が配布
Local.claude/settings.local.json自分のみ（このリポジトリ）×（gitignore）
Project.claude/settings.jsonリポジトリの全員○（git にコミット）
User~/.claude/settings.json自分（全プロジェクト）×
配列は「マージ」される

permissions.allow や hooks、sandbox.filesystem.allowWrite のような配列型の設定は置換ではなく連結・重複排除されます。低優先度のスコープでもエントリを追加できるということです。チームの settings.json に共通の許可を置き、個人の追加は settings.local.json に書く、という併用ができます。

実効設定の確認は /status、/config、/doctor で行えます。ほかの機能の置き場所も同じ規則で、スキルは ~/.claude/skills/ と .claude/skills/、CLAUDE.md は ~/.claude/CLAUDE.md と ./CLAUDE.md です（2 章）。

5-4. 権限ルールの書き方

ルールは Tool または Tool(specifier) の形式。評価順は deny → ask → allow で、最初にマッチしたものが結果を決めます（ルールの詳細度は順序を変えません）。

{
  "permissions": {
    "allow": [
      "Bash(npm run test:*)",
      "Read(./src/**)",
      "Skill(commit)"
    ],
    "ask": [
      "Bash(git push:*)"
    ],
    "deny": [
      "Bash(rm -rf *)",
      "Read(./.env)",
      "WebFetch(domain:internal.example.com)"
    ],
    "defaultMode": "acceptEdits"
  }
}
書き方意味
Bashすべての Bash 呼び出し。deny に書くとツール自体が Claude から見えなくなる
Bash(npm run build)コマンド完全一致
Bash(npm run test:*)前方一致（:*）。引数付きの実行を許す定番の書き方
Bash(aws *)ワイルドカード（* は任意位置に置ける）
Read(./.env) / Edit(src/**)パス指定
WebFetch(domain:example.com)ドメイン指定
Skill(name) / Skill(name *)スキルの完全一致／前方一致
落とし穴

広い deny ルールは、より狭い allow ルールより常に優先します。Bash(aws *) を deny しつつ Bash(aws s3 ls) だけ allow する、という書き方はできません。また Bash(command:rm *) のようなパラメータ指定は複合コマンドで回避可能なため無視され、起動時に警告が出ます（正しくは Bash(rm *)）。

試してみる：安全なコマンドを許可リストに入れる 
/permissions      # 一覧表示と、この画面からの追加・編集

npm test や git status のような安全なコマンドを allow に入れると、プロンプト疲れが消え、確認の判断力を危険な操作に温存できます。権限は /permissions から足すのが安全です（既存の settings.local.json をコピペで上書きして壊さずに済みます）。

5-5. 作業ディレクトリ境界とサンドボックス

  • 境界：Claude が書き込めるのは起動ディレクトリとそのサブディレクトリ。範囲外の読み取りは承認プロンプトの後に可能
  • 追加ディレクトリ：--add-dir / /add-dir で拡張。追加先の設定は原則読み込まれない（スキルなど一部だけ読まれる。設定ファイルの permissions.additionalDirectories で追加した場合はファイルアクセスのみ）
  • サンドボックス化された Bash：/sandbox で有効化。ファイルシステムとネットワークを分離し、権限プロンプトを減らしつつ安全に自律実行させる
  • より強い分離が必要なら dev container、Docker、VM、あるいはクラウドセッション（隔離 VM）を使う

組み込みの保護

保護何が起きるか
読み取り専用コマンドls、cat、git status 等はプロンプトなしで実行される
ネットワーク取得curl / wget は自動承認されない
コマンドインジェクション検出疑わしい Bash は許可済みでも手動承認が必要になる
フェイルクローズドどのルールにもマッチしないコマンドは既定で手動承認
WebFetch の分離別コンテキストウィンドウで処理し、プロンプトインジェクションの波及を抑える
保護されたパス.git .claude（.claude/worktrees を除く）.vscode .gitconfig .zshrc .mcp.json などへの書き込みは、bypassPermissions 以外のすべてのモードで自動承認されない。permissions.allow でも事前承認できない
試してみる：サンドボックスを有効化 
/sandbox

現在のサンドボックス状態（有効／無効、許可されたドメイン、書き込み可能パス）が表示され、その場で切り替えられます。有効にしてから curl を含む作業をさせると、権限プロンプトの回数が減るのを体感できます。

5-6. フックのライフサイクルとイベント

フックは Claude Code のライフサイクル上の特定イベントで必ず実行される、あなたのプログラムです。権限ルールが「止める・通す」の 2 択なのに対し、フックは整形・検証・通知・監査など任意の処理を差し込めます。イベントは大きく 3 つのケイデンスに分かれます。

イベント発火タイミング
SessionStart / SessionEndセッション開始・再開時／終了時
UserPromptSubmitプロンプト送信後、Claude が処理する前
PreToolUseツール実行前（ブロック可能）
PermissionRequest / PermissionDenied権限判断が必要なとき／auto モードが拒否したとき
PostToolUse / PostToolUseFailureツール成功後／失敗後
NotificationClaude Code が通知を送るとき（入力待ちなど）
Stop / StopFailureClaude の応答終了時／API エラーでターンが終了したとき
InstructionsLoadedCLAUDE.md や rules が読み込まれたとき（2-8 の診断に有用）
PreCompact / PostCompactコンテキスト圧縮の前後
PreModelSwitch / PostModelSwitchモデル切り替えの前後
ConfigChange / CwdChanged / FileChanged設定変更／作業ディレクトリ変更／監視ファイル変更
WorktreeCreate / WorktreeRemoveworktree 作成・削除

サブエージェントや外部連携に関するイベント（SubagentStart、Elicitation など）もありますが、本資料の範囲外です。全一覧は公式リファレンスを参照してください。

5-7. フックの設定・入出力・ユースケース

設定ファイル（~/.claude/settings.json、.claude/settings.json など。5-3）の hooks キーに定義します。/hooks メニューからも編集できます。

{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Write|Edit",
        "hooks": [
          { "type": "command", "command": "jq -r '.tool_input.file_path' | xargs npx prettier --write" }
        ]
      }
    ]
  }
}

入出力の約束ごと

  • 入力：イベントの JSON コンテキストが stdin（コマンドフック）または POST ボディ（HTTP フック）で渡される。編集対象のパスを受け取る環境変数は用意されていないので、jq -r '.tool_input.file_path' のように stdin の JSON から取り出す（環境変数で渡るのは CLAUDE_PROJECT_DIR などに限られる）
  • 出力その 1（終了コード）：exit 0 = 通過、exit 2 = ブロックし、stderr の内容が Claude へのフィードバックになる
  • 出力その 2（構造化 JSON）：exit 0 ＋ JSON で決定を細かく制御。exit 2 と JSON の併用は不可
  • フックの種類は 5 つ：command（シェル）／http（POST）／mcp_tool／prompt（LLM に判定させる）／agent（サブエージェントで検証）。prompt・agent 型は発火は決定論的でも判定はモデルに委ねるので確率的
#!/bin/bash
# PreToolUse: 危険な SQL をブロックする例
INPUT=$(cat)                                            # stdin の JSON を受け取る
COMMAND=$(echo "$INPUT" | jq -r '.tool_input.command')  # 実行されようとしているコマンド
if echo "$COMMAND" | grep -q "DROP TABLE"; then
  echo "Blocked: dropping tables is not allowed" >&2    # stderr が Claude へのフィードバック
  exit 2                                                # exit 2 = ブロック
fi
exit 0

典型的なユースケース

PostToolUse
編集後の自動整形・検証

Write/Edit にマッチさせて Prettier・gofmt・ruff や Lint を実行。結果はテキストとして Claude に返り、機械的な合否を毎周回のコンテキストに入れる（3-6 ループ）を人手なしで成立させる。

PreToolUse
保護ファイルの編集を遮断

.env、本番設定、マイグレーション済みファイルへの書き込みを exit 2 で拒否。

Notification
入力待ちを通知

Claude が確認を求めたときに OS 通知・Slack・LINE などへ ping。

Stop
ターン終了時の検証

作業ツリー全体をスキャンして未整形・未テストを検出。exit 2 で返せば、通るまで作業を終えさせない。

PostCompact
圧縮後の再注入

コンパクションで失われがちな重要コンテキストを再投入する。

ConfigChange
設定変更の監査

セッション中の設定変更を記録、あるいはブロックする。

Bash 経由の変更に注意

Claude は Bash ツールからもファイルを変更できます。すべての変更を捕捉したい監査用途では、ターンごとに 1 回作業ツリーを走査する Stop フックを併用してください。

スコープとトラブルシューティング

  • フックはマージされる。ユーザー設定・プロジェクト設定・スキル定義の全てが該当イベントで発火する
  • プロジェクト設定のフックは、そのフォルダのワークスペーストラストを承認した後に有効になる
  • スクリプトは ${CLAUDE_PROJECT_DIR} を使って絶対パスで参照すると安定する
  • 発火しないときは /hooks で登録状況を確認し、スクリプトを手動実行して終了コードを検証する
echo '{"tool_name":"Bash","tool_input":{"command":"ls"}}' | ./my-hook.sh
echo $?   # 終了コードを確認
セキュリティ

フックはあなたの権限で任意のシェルコマンドを実行します。他人が書いたフック（リポジトリ由来・配布物）は、信頼する前に必ず中身を読んでください。

試してみる：最小のフックを入れる 
/hooks        # メニューから対話的に追加するのが最も安全

ファイルで書くなら以下。.claude/settings.local.json が既にある場合は上書きされるので、既存があるときは手で追記してください。

mkdir -p .claudecat > .claude/settings.local.json <<'EOF'
{
  "hooks": {
    "Stop": [
      { "matcher": "", "hooks": [
        { "type": "command", "command": "echo \"turn finished at $(date)\" >> \"$CLAUDE_PROJECT_DIR/.claude/hook.log\"" }
      ]}
    ]
  }
}
EOF

セッションを開き直し、/hooks で登録を確認。1 ターン話すと .claude/hook.log が増えます。後始末は .claude/settings.local.json の hooks ブロックを削除。

5-8. 組織の管理設定

個人利用なら既定のままでも動きますが、チーム・組織で使うなら、技術的な強制は「管理設定」、行動指針は「管理 CLAUDE.md」と役割を分けます。設定ルールは Claude の判断に関係なくクライアントが強制しますが、CLAUDE.md はあくまで指示です。

テーマ手段
ポリシー配布管理設定（MDM / グループポリシー / managed-settings.json）、サーバー管理設定。個人・プロジェクト設定では上書きできない（5-3）
認証の統制forceLoginMethod、forceLoginOrgUUID、SSO。個人アカウントでの無管理利用を防ぐ
行動指針の統一管理 CLAUDE.md（除外不可。2-2）
モデルと努力レベルの制限availableModels 許可リスト、組織デフォルトモデル、努力レベル上限
権限の強制管理設定の permissions.deny（機密パス・危険コマンド）、defaultMode、サンドボックスの強制、disableSkillShellExecution
データ保護データ利用ポリシー、ゼロデータ保持（ZDR、対象アカウント）

データはどこへ行くか

導入審査で最初に問われる論点です。送信されるのはコンテキストに入ったもの、つまりあなたのプロンプト、Claude が読んだファイルの内容、実行したコマンドの出力、CLAUDE.md や読み込まれたルールです。裏返すと、リポジトリ全体が自動でアップロードされるわけではありません。

アカウント学習への利用データ保持
商用（Team / Enterprise / API / Bedrock 等）コードやプロンプトを生成モデルの学習に使わない（Development Partner Program に明示的にオプトインした場合を除く）商用条件に従う。対象アカウントはゼロデータ保持（ZDR）も選択可
コンシューマー（Free / Pro / Max）設定で選択できる。許可すると新モデルの学習に使われる許可時は 5 年、不許可なら 30 日

プロンプトインジェクション

Web ページ、Issue、ログなど外部から取り込んだ内容は「データ」であって「指示」ではない、が基本原則です。製品側は権限システム・入力サニタイズ・ネットワークコマンドの承認・分離コンテキストでの Web fetch・信頼検証で多層防御し、利用者側は承認前にコマンドを読む、信頼できないコンテンツを直接パイプしない、重要ファイルの変更差分を確認する、で守ります。-p の非対話実行では信頼検証が無効になる点に注意してください。

導入リスクと緩和策

リスク何が起きるか緩和策
機密情報の外部送信秘密鍵や個人情報を含むファイルを Claude が読み、送信されるdeny ルール（Read(./.env) 等）、/sandbox、管理設定で強制、必要なら ZDR
