05

ベストプラクティス

公式の ベストプラクティス（旧 Anthropic Engineering の記事が統合されたページ）を、 「環境づくり」「対話」「セッション管理」「スケール」「失敗パターン」の 5 つに整理します。

原理との対応

この章は図 1-1 の核のうちエージェントループの運用そのもので、根拠は 3-9 ループ（ループは、機械的な合否がコンテキストに入る領域でだけ収束する）です。各節は、その収束条件を満たすための工夫として読めます——検証手段を与える（5-1）は合否をコンテキストに入れる工夫、探索 → 計画 → 実装とインタビューさせる（5-1・5-3）は外れた周回を減らす工夫、2 回失敗したら /clear（5-4）は失敗案が積もったコンテキストを捨てて収束を取り戻す工夫（3-9 コンテキスト）、Writer と Reviewer を分ける（5-4）は別のコンテキストで検証を回す工夫（3-9 メモリ）です。廃れないのは「合否が返る仕事なら任せられ、返らない仕事は見張る」という判断基準で、変わるのはコマンド名・推奨される手順・ツール名です。

5-1. 3 つの基本原則

01
検証手段を与える

テスト、ビルド、比較用スクリーンショット。Claude が自分でチェックできるかどうかが、「見張るセッション」と「任せられるセッション」を分ける。長時間任せるなら、完了条件を /goal に置くと毎ターン後に別の評価器が判定してくれる（6-5）。

02
探索 → 計画 → 実装

調査と実装を分けると、間違った問題を解くことを防げる。ただし小さく明確な修正に Plan Mode は不要（オーバーヘッドになる）。

03
具体的なコンテキストを渡す

対象ファイル、制約、参考にすべき既存パターンを明示する。最初のプロンプトの精度が、後の手戻りを決める。

チェックアウトフローが、期限切れカードのユーザーで壊れています。
src/payments/ を、特にトークン更新まわりを中心に確認してください。
まず失敗するテストを書いて、その後で修正してください。

5-3. 対話の技法

  • 会話として扱う：完璧なプロンプトは不要。まず投げて、そこから修正する
  • 中断して操舵する：Esc で即停止、あるいは実行中に補足を送る
  • 委譲する（指示しすぎない）：読むファイルや実行コマンドを逐一指定せず、目的と制約を伝える
  • コードベースへの質問に使う：「ロギングはどう動く？」「なぜ 333 行目で foo() を呼ぶ？」——オンボーディングに極めて有効
  • 逆にインタビューさせる：大きめの機能では AskUserQuestion で Claude に質問させ、仕様を SPEC.md に落としてから、新しいセッションで実装させる
[brief description] を作りたい。AskUserQuestion ツールで詳しくインタビューしてください。
技術実装、UI/UX、エッジケース、懸念、トレードオフについて。
自明な質問は不要。私が見落としていそうな難所を掘ってください。
一通り終わったら SPEC.md に完全な仕様を書いてください。

5-4. セッション管理とスケール

管理

原則はひとつ、同じ問題で 2 回修正したらコンテキストは汚れている——/clear して、学んだことを織り込んだプロンプトで再スタートします。具体的な操作（/clear・/compact <focus>・/rename）は 7-6、チェックポイントと /rewind は 3-7 にまとめてあります。

スケール

  • 非対話モードで CI・スクリプトに組み込む
  • worktree / デスクトップ / クラウドで並列セッション。Writer と Reviewer を分けると品質が上がる。Reviewer を新しいサブエージェントとして走らせれば、実装に至った思考を知らないまま差分だけを評価するため確証バイアスが入りにくい
  • 大量ファイルはループ＋claude -p でファンアウト（まず 2〜3 件で検証してから全件）
  • 長時間の自律実行には auto モード＋敵対的レビューを組み合わせる

5-5. よくある失敗パターン

アンチパターン症状対処
キッチンシンク・セッション1 つのセッションで無関係な話題を行き来し、コンテキストが雑多になるタスクの切れ目で /clear
修正の連鎖間違い → 修正 → まだ間違い、の繰り返しで失敗案が蓄積2 回失敗したら /clear して初期プロンプトを書き直す
過剰な CLAUDE.md長すぎて重要なルールがノイズに埋もれる容赦なく削る。守らせたいものはフックへ
信頼して検証しないそれらしい実装だがエッジケースを落としている常に検証手段（テスト・スクリプト・スクショ）を与える
無限探索スコープなしの「調査して」で数百ファイルを読む調査範囲を絞る／サブエージェントに委譲する
最後に

公式ドキュメント自身が述べているとおり、これらのパターンは固定ルールではありません。うまくいったときに何をしたかを観察し、自分のプロジェクトに合った直感を育てることが最終的な到達点です。

5-6. この章の持ち帰り

公式のベストプラクティスから、効果が大きく、今日から変えられるものだけを抜きました。

覚えること仕事での効き目具体的な操作
ループは合否が返る領域でだけ収束するこの章の推奨はすべて「合否をコンテキストに入れる」「外れた周回を減らす」「失敗案を捨てる」のどれか。新しい推奨が出ても同じ 3 つに分類でき、自分の仕事に効くかを判断できる3-9 ループ の 3 条件で仕事を見る
同じ問題で 2 回失敗したら /clear失敗案が積み上がったコンテキストは、そのまま続けても精度が上がらない。作り直すほうが速い/clear → 学んだことを織り込んで再依頼
必ず検証手段を渡す「見張るセッション」と「任せられるセッション」を分ける最大の要因。テスト・ビルド・スクショのどれかを持たせる「まず失敗するテストを書いて、その後で修正して」
Writer と Reviewer を分ける実装に至った思考を知らないレビュアーは確証バイアスが入りにくい。見落としの検出率が上がる新しいサブエージェントに差分だけ見せる
大きい機能は先にインタビューさせる仕様の抜けを実装前に潰せる。SPEC.md が残るのでレビューや引き継ぎにも効くAskUserQuestion で質問させ、SPEC.md に落として新しいセッションで実装
安全なコマンドを許可リストに入れるプロンプト疲れが消え、確認の判断力を危険な操作に温存できる/permissions に Bash(npm test:*) など
意外と知られていない

小さく明確な修正に Plan Mode は不要です。公式も「オーバーヘッドになる」と明記しています。プランモードは間違った問題を解くリスクが高いとき——影響範囲が読めない、方針が複数ある、既存設計に合わせる必要がある——に限って使うのが、実は最も生産性が高い使い方です。
