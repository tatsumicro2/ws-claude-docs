# AI エージェントのコア技術ロードマップを作らせるプロンプト

作成日：2026-09-08（既存資料の再利用を前提に再構築）

## これは何か

Claude Code を「コマンドを覚える対象」ではなく「AI エージェントの一実装」として捉え直すための
学習ロードマップを、AI に作らせるためのプロンプト。

**ゼロから書かせない。** 本リポジトリの `claude-code-guide/`（全 19 章 / 116 節）には、
4 層のコア技術のうち相当部分がすでに書かれている。書き足すのは欠けている分だけで、
すでにあるものは**参照でつなぐ**。これがこのプロンプトの中心的な指示。

### 元案から引き継いだ検証条項

元になった案（外部の AI が生成したもの）は骨格は妥当だったが、事実面で 4 点が危うかった。
そのまま再生産させないよう、検証を強制する条項を組み込んである。

| 元案の記述 | 問題 |
|---|---|
| 「Claude 3.5 Sonnet の 200k トークン」 | モデル世代・コンテキスト長ともに古い。要再確認 |
| 「Lost in the Middle 現象」 | 2023 年の論文（Liu et al.）。検証対象モデルが古く、現行モデルに当てはまるかは未検証 |
| 「ReAct が Claude Code の思考ループの基盤」 | ReAct は概念モデル。公式は「収集 → 実行 → 検証」の 3 フェーズで説明しており、実装根拠ではない |
| 「LangGraph は Claude Code の設計思想そのもの」 | 断定できない。内部実装は非公開 |

## 使い方

下の「プロンプト本体」をそのまま渡す。リポジトリのルートで実行させること
（既存資料を読ませる前提のため、別の場所で実行しても機能しない）。

## プロンプト本体

```text
# 依頼

Claude Code を「コマンドを覚える対象」ではなく「AI エージェントの一実装」として理解するための
学習コンテンツを、**このリポジトリの既存資料を再利用して**再構築してください。

新規に文章を量産するのではなく、
「すでに書かれているもの」「書かれていないもの」を切り分け、後者だけを書き足すのが目的です。

## 前提と狙い

読者は Claude Code を日常的に使っているが、スラッシュコマンドやオプションの暗記に留まっている。
この状態の問題は次の 3 つで、成果物はこれを解消するものであること。

1. ツールの限界を予測できない（なぜ失敗したのかを構造で説明できない）
2. 指示の設計ができない（うまくいくプロンプトを再現性なく引いている）
3. 別のツールに乗り換えたときに知識が消える

したがって扱うのは「Claude Code の機能」ではなく、
Claude Code を含む自律型エージェント一般が依存しているコア技術である。

## 手順（この順に実行すること。棚卸しを飛ばして書き始めない）

### 手順 1：既存資料の棚卸し

`claude-code-guide/toc.json` で全 19 章 / 116 節の構成を把握したうえで、
下記 4 層のそれぞれについて、**既存のどの節がすでに答えているか**を本文まで読んで確認し、
「層 × 既存節 × 状態（足りている／部分的／欠けている）」の表を作る。

対象とする 4 層（この分類自体の妥当性も手順 2 で検証する）：

- ① 言語モデルの推論特性（トークン、コンテキスト、システムプロンプトの位置づけ）
- ② ツール使用 / 関数呼び出し（スキーマ定義、構造化出力、実行系への受け渡し）
- ③ 思考と行動の反復ループ（思考 → 行動 → 観察、失敗の自己修正）
- ④ 状態と記憶の管理（履歴の圧縮・要約、セッションをまたぐ永続化）

**下表は調査済みの仮説であり、確定した結論ではない。** 本文を読んで裏を取り、
誤りがあれば訂正し、見落としがあれば追加すること。

| 層 | すでに答えている既存節（仮説） | 状態（仮説） |
|---|---|---|
| ① 推論特性 | 1-2（関数＝モデル。記憶も副作用も持たない）、3-3 モデルと努力レベル、3-6 コンテキストウィンドウ、7-2 何がトークンを消費するのか、7-4 言語ごとのトークン量（実測値あり）、7-3 プロンプトキャッシュ | 部分的。「次に来る語を予測している」という推論の原理そのものと、システムプロンプトの位置づけが無い |
| ② ツール使用 | 1-2（モデルは「編集したい」と書くだけで、動かすのはハーネス）、3-4 組み込みツール、3-5 操作できる範囲、3-8 ツール別の落とし穴、13-1 MCP の位置づけ、9-5 機能別のコンテキストコスト、16-4 Agent SDK | 部分的。ツール定義のスキーマと、モデルの出力を実行に変換する経路が無い（資料全体で "JSON Schema" は 16 章の 1 行のみ） |
| ③ 思考ループ | 3-1 エージェントループ（収集 → 実行 → 検証の図あり）、3-2 エージェントハーネス、1-2 の「3 つから導けること」の表、5-1 3 つの基本原則、5-5 よくある失敗パターン | 概ね足りている。概念モデル（ReAct 等）との対応づけと、自己修正が効く条件・効かない条件が無い（"ReAct" は資料に 1 度も出てこない） |
| ④ 状態と記憶 | 3-6 コンテキストウィンドウ、3-7 セッション・チェックポイント・巻き戻し、4 章全体（CLAUDE.md と自動メモリ）、7-3 プロンプトキャッシュ、7-6 使用量の削減、7-7 想定より多いときの診断、11-1 コンテキスト分離の効果 | ほぼ足りている。要約・圧縮アルゴリズムの一般論と、状態を明示的に持つ設計（グラフ型など）が無い |

### 手順 2：抽象が三重にならないか判定する

**これが最も重要な判定である。**
本資料はすでに 2 つの抽象を持っている。

- 1-2「本質 — 突き詰めると 3 つしかない」：文字列・関数・ループへの還元
- 1-9「全体像 — 1 回のプロンプトが通る道」：入口・状態・中心・拡張・制御・運用の地図

ここに 4 層を**第 3 の互換性のない抽象として並べると、読者は確実に混乱する。**
次のいずれかを選び、理由とともに明示すること。

- (A) 4 層を既存の 2 つに対応づけて提示する（対応表を必ず作る）
- (B) 4 層という枠組みを捨て、既存の抽象の下に不足分を配置する
- (C) 4 層で既存の抽象を置き換える（既存を書き換える提案とセットで出すこと）

安易に (A) を選ばない。対応が不自然になるなら (B) を選ぶほうが読者のためになる。

### 手順 3：書くものを決める

- **「足りている」と判定した内容は書き直さない。** 既存節へのリンクで参照する
- **新規に書くのは「部分的」「欠けている」と判定した分だけ**
- 既存の記述と矛盾する内容を書かない。矛盾を見つけた場合は新規に書くのではなく、
  「既存 N-M の修正案」として別立てで報告する

新規に書く各項目には、必ず次の 4 つを含める。

- 何か：仕組みを 1 段掘った説明。比喩で終わらせない
- なぜ必要か：これが無いと何ができなくなるか
- これを知ると何が説明できるようになるか：日常で遭遇する現象を最低 2 つ、
  「原因 → 現象」の形で対応づける（例：「毎ターン全履歴を送り直す」→「会話が伸びると遅く・高くなる」）
- 誤解されやすい点：混同しがちな概念と、その区別

### 手順 4：配置を提案する

新章として立てるか、既存章への追記にするかを判定し、理由を述べる。
判定基準：**新規に書く分量が 1 章分に満たないなら、新章にしない。**
その場合はどの節の直後に何を足すかを、節単位で具体的に示す。

なお現時点の見立てでは、既存の 3 章（コアメカニズム）の前段または内部への追記が
最も噛み合う可能性が高い。ただしこれは仮説であり、手順 1 の結果で覆してよい。

### 手順 5：実践ステップを付ける

読むだけで終わらせないため、手を動かす順序を示す。
各ステップに**到達判定（何ができたら次に進んでよいか）**を必ず付ける。
「作る → 読む → 比べる」の順を基本とし、いきなりフレームワークから入らせない。
既存の 17 章（学習ロードマップ）と重複する内容は書かず、17 章への参照で済ませる。

### 手順 6：限界を書く（必須）

最後に「このロードマップの限界」を 1 節設け、以下を論じる。

- 概念モデル（思考ループのフレームワーク等）と、実際の製品実装の距離
- 原理を学んでも解決しない領域はどこか
- フレームワーク学習が目的化する失敗パターン

## 事実の扱い（最重要）

- **モデル名・コンテキスト長・価格・API の仕様を、記憶から書かないこと。**
  必ず現時点の一次情報（Anthropic 公式ドキュメント、API リファレンス）を確認し、
  確認日と参照元を添える。確認できなかったものは「未確認」と明記して残す。
- **Claude Code の内部実装は非公開である。** 記述は次の 3 つに分類してラベルを付け、混ぜない。
  (a) 公式に文書化された挙動　(b) 観測できる挙動　(c) 他の OSS エージェントからの類推
- **論文由来の知見には、発表年と検証対象モデルを添える。**
  古いモデルで観測された現象を現行モデルにそのまま当てはめない。不明なら「未検証」と書く。
- 数値を書くなら、可能な限り手元で実測してから書く。推測値を置かない。
- 出典は公式ドキュメント。日本語版が英語版より古い箇所は英語版に従い、その旨を注記する。
  コミュニティ資料は事例収集にのみ使い、仕様の根拠にしない。

## 禁止事項

- コマンドやオプションの一覧（この資料の目的の逆）
- 既存節に書かれている内容の書き直し・言い換え
- 「〜と言われています」「一般的には」など出典を伴わない断定
- 特定フレームワークが唯一の正解であるかのような書き方
- 4 層のような分類を、根拠を示さずに「定説」として提示すること

## 出力

次の 5 部構成で、日本語で出力する。

1. **棚卸し表**（手順 1 の結果。仮説からの訂正点を明示）
2. **抽象の判定**（手順 2。(A)(B)(C) のどれを選び、なぜか）
3. **新規に書く内容**（手順 3。既存で足りる部分は参照リンクで済ませる）
4. **配置の提案**（手順 4。新章 or 節単位の追記先）
5. **限界**（手順 6）＋ 参照した一次情報の URL 一覧と確認日

## 最後に自己点検

出力前に次を確認し、満たしていない項目があれば書き直してから出すこと。

- [ ] 棚卸しを実際に本文まで読んで行ったか（toc.json のタイトルだけで判定していないか）
- [ ] 既存節の書き直しになっている箇所は無いか
- [ ] 抽象が三重になっていないか（手順 2 の判定を明示したか）
- [ ] 新規に書いた各項目に「説明できるようになる現象」が 2 つ以上あるか
- [ ] 一次情報で確認していない数値・モデル名が残っていないか
- [ ] (a)(b)(c) のラベル分けができているか
- [ ] 実践ステップに到達判定が付いているか
- [ ] 限界を論じた節があるか
```

## 追加要件（HTML 章として書き出させる場合）

手順 4 で「新章を立てる」または「既存章へ追記する」と判定が出て、
実際に HTML を書かせる段階になったら、上のプロンプトの末尾に次を足す。

```text
## 追加要件（claude-code-guide の編集規約）

- 節の単位は `<article class="slide" id="sN-M" data-slide="N-M" data-slide-title="…">`
- `<h3>N-M. タイトル</h3>` の「タイトル」は data-slide-title と完全一致させる。h3 の中にタグを入れない
- 節を足したら `toc.json` の `sections` にも追記する（toc.json が章・節構成の唯一のソース）
- `<!-- NAV:START -->` `<!-- PAGER:START -->` `<!-- INDEX:START -->` の区間は自動生成。手で触らない
- `claude-code-guide/_source/index.html` は更新しない
- 章を新設する場合は、末尾に「この章の持ち帰り」節を既存章と同じ体裁
  （覚えること／仕事での効き目／具体的な操作）で置く
- 表で順序のある軸を扱うときは「上ほど高い／強い／深い」で統一する
- 「試してみる」ブロックは、シェルコマンドとセッション内コマンドを混ぜない
- 編集後は `python3 tools/build_nav.py` → `python3 tools/check_docs.py` を順に実行し、
  `OK` が出るまで終えない
```
