15

設定・権限・セキュリティ

個人利用なら既定のままでも動きますが、チーム・組織で使うならこの章が本番です。 設定の階層、権限ルール、サンドボックス、企業向けデプロイまでを押さえます。

原理との対応

この章は図 1-1 のガードレールの実装で、根拠は 3-9 ガードレール（副作用はハーネスにしかない）です。モデルは「実行したい」と言うだけで、外界に触れるのはハーネスだけなので、止められる場所はツール実行の直前の 1 か所に集まります。権限ルール（15-3）、サンドボックス、保護されたパス（15-4）、組織の管理設定（15-7）はすべてその 1 か所に置く強制の書き方で、設定の階層（15-1・15-2）は「誰の強制が勝つか」の決め方です。CLAUDE.md は同じ場所に届かない「文脈で頼む」側だと切り分けてください。データの外部送信（15-6）は 3-9 コンテキスト に結びつきます——送られるのはコンテキストに入ったもの、つまり Claude が読んだファイル・コマンド出力・CLAUDE.md であり、それ以上でもそれ以下でもありません。廃れないのは「実行直前で止める」「コンテキストに入れたものが送られる」の 2 つの構造で、変わるのはルール構文、保護パスの一覧、保持期間の数値です。

15-3. 権限ルールの書き方

ルールは Tool または Tool(specifier) の形式。評価順は deny → ask → allow で、最初にマッチしたものが結果を決めます（ルールの詳細度は順序を変えません）。

{
  "permissions": {
    "allow": [
      "Bash(npm run test:*)",
      "Read(./src/**)",
      "Skill(commit)"
    ],
    "ask": [
      "Bash(git push:*)"
    ],
    "deny": [
      "Bash(rm -rf *)",
      "Read(./.env)",
      "WebFetch(domain:internal.example.com)"
    ],
    "defaultMode": "acceptEdits"
  }
}
書き方意味
Bashすべての Bash 呼び出し。deny に書くとツール自体が Claude から見えなくなる
Bash(npm run build)コマンド完全一致
Bash(aws *)ワイルドカード（* は任意位置に置ける）
Read(./.env) / Edit(src/**)パス指定
WebFetch(domain:example.com)ドメイン指定
mcp__github / mcp__github__create_issueMCP サーバー単位／ツール単位
Skill(name) / Skill(name *)スキルの完全一致／前方一致
Agent(model:opus)入力パラメータでのマッチ（deny / ask のみ）
落とし穴

広い deny ルールは、より狭い allow ルールより常に優先します。Bash(aws *) を deny しつつ Bash(aws s3 ls) だけ allow する、という書き方はできません。また Bash(command:rm *) のようなパラメータ指定は複合コマンドで回避可能なため無視され、起動時に警告が出ます（正しくは Bash(rm *)）。

試してみる：権限ルールを1つ足す 
/permissions      # 一覧表示と、この画面からの追加・編集

権限は /permissions から足すのが安全です（12-3 でフックを書いた .claude/settings.local.json を、コピペで上書きして壊さずに済みます）。手で書く場合は同じファイルの permissions キーに追記してください。

15-4. 作業ディレクトリ境界とサンドボックス

  • 境界：Claude が書き込めるのは起動ディレクトリとそのサブディレクトリ。範囲外の読み取りは承認プロンプトの後に可能
  • 追加ディレクトリ：--add-dir / /add-dir で拡張。設定は原則読み込まれず、例外は下表の 4 つだけ（設定ファイルの permissions.additionalDirectories で追加した場合は例外が一切適用されず、ファイルアクセスのみ）
  • サンドボックス化された Bash：/sandbox で有効化。ファイルシステムとネットワークを分離し、権限プロンプトを減らしつつ安全に自律実行させる
  • より強い分離が必要なら dev container、Docker、VM、あるいはクラウドセッション（隔離 VM）を使う
設定の種類--add-dir から読み込まれるか
.claude/skills/○（ライブリロードあり）
.claude/commands/○（ライブリロードなし。プロジェクト側と同名ならプロジェクト側が優先）
.claude/agents/○（ライブリロードなし）
.claude/settings.jsonenabledPlugins と extraKnownMarketplaces キーのみ
CLAUDE.md / .claude/rules/ / CLAUDE.local.mdCLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1 のときのみ

組み込みの保護

保護何が起きるか
読み取り専用コマンドls、cat、git status 等はプロンプトなしで実行される
ネットワーク取得curl / wget は自動承認されない
コマンドインジェクション検出疑わしい Bash は許可済みでも手動承認が必要になる
フェイルクローズドどのルールにもマッチしないコマンドは既定で手動承認
WebFetch の分離別コンテキストウィンドウで処理し、プロンプトインジェクションの波及を抑える
認証情報macOS Keychain 等に安全に保存される
保護されたパス.git .claude（.claude/worktrees を除く）.vscode .gitconfig .zshrc .mcp.json などへの書き込みは、bypassPermissions 以外のすべてのモードで自動承認されない。permissions.allow でも事前承認できない
試してみる：サンドボックスを有効化 
/sandbox

現在のサンドボックス状態（有効／無効、許可されたドメイン、書き込み可能パス）が表示され、その場で切り替えられます。有効にしてから curl を含む作業をさせると、権限プロンプトの回数が減るのを体感できます。

15-5. プロンプトインジェクション対策

Web ページ、Issue、ログ、MCP のレスポンスなど外部から取り込んだ内容は「データ」であって「指示」ではない——これが基本原則です。Claude Code 側の防御と、利用者側の運用の両輪で守ります。

製品側
多層防御

権限システム、コンテキスト認識分析、入力サニタイズ、ネットワークコマンドの承認、分離コンテキストでの Web fetch、信頼検証。

利用者側
運用ルール

承認前にコマンドを読む。信頼できないコンテンツを直接パイプしない。重要ファイルの変更差分を確認。VM を使う。

  • 初回のコードベース実行と新規 MCP サーバーには信頼検証が入る（-p の非対話実行では無効になる点に注意）
  • 疑わしい挙動は /feedback で報告

15-6. データの外部送信範囲

導入審査で最初に問われる論点です。攻撃対策（15-5）とは別に、自社コードがどこへ行き、学習に使われるのかを押さえます。

送信されるもの

  • あなたのプロンプト、Claude が読んだファイルの内容、実行したコマンドの出力、CLAUDE.md や読み込まれたルール
  • 裏返すと、リポジトリ全体が自動でアップロードされるわけではありません。Claude が読んだ範囲だけが送信されます
  • 実行環境によって経路が変わります：ローカル実行（コードはローカル、API 呼び出しのみ外部）／クラウドセッション（Anthropic 管理 VM 上で実行）／Bedrock・Google Cloud・Foundry 経由（自社のクラウド契約内で処理）

モデル学習への利用

アカウント学習への利用データ保持
コンシューマー（Free / Pro / Max）設定で選択できる。許可すると新モデルの学習に使われる許可時は 5 年、不許可なら 30 日
商用（Team / Enterprise / API / Bedrock 等 / Gov）コードやプロンプトを生成モデルの学習に使わない（Development Partner Program に明示的にオプトインした場合を除く）商用条件に従う。対象アカウントはゼロデータ保持（ZDR）も選択可
  • /feedback で送ったトランスクリプトは 5 年間保持されます
  • セッション品質調査でトランスクリプトが送られるのは、明示的に Yes を選んだときだけです（CLAUDE_CODE_DISABLE_FEEDBACK_SURVEY=1 で無効化可能）
  • 実務のガード：deny で Read(./.env) や機密ディレクトリを塞ぐ／/sandbox で分離／--add-dir の運用ルールを決める／組織では管理設定で強制

15-8. 導入リスクと緩和策

Bash(aws *) を deny しつつ Bash(aws s3 ls) だけ allow する、という書き方はできません。広い deny が常に勝つためで、権限設計でいちばん多いつまずきです。もう一つ、導入審査でよく誤解される点——リポジトリ全体が自動でアップロードされるわけではありません。送信されるのは Claude が実際に読んだ範囲だけです。商用アカウント（Team / Enterprise / API）はコードを生成モデルの学習に使いません。
