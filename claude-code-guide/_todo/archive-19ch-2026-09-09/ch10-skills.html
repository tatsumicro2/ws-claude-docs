10

Skills（スキル）

スキルは最も柔軟な拡張手段です。実体は SKILL.md という Markdown ファイル 1 枚。 Claude が自動で読み込むことも、/名前 であなたが呼び出すこともできます。

原理との対応

スキルは、図 1-1 の「拡張」のうち手順知識を担う要素で、コンテキストウィンドウに必要になった時点で差し込む仕組みです（3-9 コンテキスト）。常駐するのは description だけで、本文は呼び出されたときに初めてコンテキストに足され、以後はセッションの終わりまで残ります（10-4・10-6）。手順をファイルに書いて次のセッションでも使えるようにする点は、「外に残す」の一種で（3-9 メモリ）、CLAUDE.md が「毎回先頭に置く」のに対し、スキルは「要るときだけ足す」という違いがあります。ただし足されるのはコンテキストであって、モデルに守らせる力はありません——スキルは文脈であって強制ではない（3-9 ガードレール）ので、必ず走らせたい処理はフック（12 章）へ置きます。廃れないのは「要るときだけコンテキストに足す」という遅延ロードの設計と、それが依頼にすぎないという事実で、変わるのはフロントマターのフィールド名や切り詰めの文字数、ディレクトリの規約です。

10-1. スキルの基本

  • ディレクトリに SKILL.md を置くだけで、Claude のツールキットに手順・知識が追加される
  • 本文は使用時にしか読み込まれないため、長い参照資料でも普段はほぼ無コスト
  • カスタムコマンド（.claude/commands/*.md）はスキルに統合済み。両者とも /deploy として動作するが、スキルの方が高機能（補助ファイル、呼び出し制御、自動発火）
  • Claude Code のスキルは Agent Skills オープン標準に準拠。他の AI ツールとも互換性がある

作成する目安

同じプレイブック・チェックリスト・複数ステップの手順を繰り返し貼り付けているとき、または CLAUDE.md の一節が「事実」ではなく「手順」に育ってきたとき。

10-2. 最小構成とディレクトリ構造

mkdir -p ~/.claude/skills/summarize-changes
---
description: 未コミットの変更を要約し、危険な点にフラグを立てる。差分レビューやコミットメッセージを求められたときに使う。
---

## Current changes

!`git diff HEAD`

## Instructions

上記の変更を 2〜3 個の箇条書きで要約し、エラー処理の欠落・
ハードコードされた値・更新が必要なテストなどのリスクを列挙してください。

ディレクトリとしてのスキル

my-skill/
├── SKILL.md          # メイン指示（必須）
├── reference.md      # 詳細な API ドキュメント（必要時に読む）
├── examples/
│   └── sample.md
└── scripts/
    └── validate.sh   # Claude が実行できるスクリプト

SKILL.md は 500 行以下を目安に。詳細は補助ファイルへ逃がし、SKILL.md から参照させます。冒頭の --- で挟まれた部分は フロントマター（YAML 形式の設定ブロック）と呼び、次節で扱います。

試してみる：30秒でスキルを作る 
mkdir -p ~/.claude/skills/summarize-changes && cat > ~/.claude/skills/summarize-changes/SKILL.md <<'EOF'
---
description: 未コミットの変更を要約する。差分レビューを求められたときに使う。
---
!`git diff HEAD --stat`

上の変更を3行で要約し、気になる点を挙げてください。
EOF

前提：git リポジトリ内で実行してください。~/.claude/skills/ をこの手順で初めて作った場合は Claude Code の再起動が必要です（2 つ目以降のスキルは再起動不要）。
後始末：rm -rf ~/.claude/skills/summarize-changes

10-3. スキルの置き場所と優先順位

場所パス適用範囲
Enterprise管理設定ディレクトリ組織内の全ユーザー
Personal~/.claude/skills/<name>/SKILL.md全プロジェクト
Project.claude/skills/<name>/SKILL.mdそのプロジェクトのみ
Plugin<plugin>/skills/<name>/SKILL.mdプラグイン有効時（/plugin:name）
  • 同名なら enterprise > personal > project。バンドルスキルも同名の自作スキルで上書きできる。claude.ai アカウントから同期されたスキルは最下位で、上記いずれのソースでも上書きされる
  • モノレポではネストした .claude/skills/ も検出され、/apps/web:deploy のような修飾名で呼び分けられる
  • ライブ変更検出：SKILL.md の追加・編集は再起動なしで反映される（新規のトップレベルディレクトリ作成時のみ再起動が必要）

10-4. 主要フロントマターフィールド

フィールド説明
description実質必須。Claude が「使うべきか」を判断する材料。主要ユースケースを先頭に書く
when_to_useトリガーフレーズや例示。description と合わせて 1,536 文字で切り詰められる
name表示名。呼び出し名は原則ディレクトリ名から決まる
disable-model-invocationtrue で Claude の自動発火を禁止＝ユーザー専用。副作用のある操作に必須級
user-invocablefalse で / メニューから隠す＝Claude 専用の背景知識向け
allowed-tools確認なしで使えるツール（例 Bash(git add *)）。有効なのは呼び出したそのターンだけで、次のメッセージを送ると解除される（本文はコンテキストに残るが権限は残らない）。セッション全体に効かせたいなら permissions.allow に書く
disallowed-tools実行中に取り除くツール
context: forkサブエージェントの分離コンテキストで実行する
agentfork 時に使うサブエージェント種別（Explore / Plan / カスタム）
model / effortこのスキル実行中のモデル・努力レベル
paths該当ファイルを扱うときだけ自動発火させる glob
argument-hint / arguments補完に出す引数ヒント／名前付き引数の定義
hooksこのスキルのライフサイクルに限定したフック

呼び出し制御の組み合わせ

設定ユーザーClaudeコンテキストへの読み込み
（既定）可可説明は常時／呼び出しで全文
disable-model-invocation: true可不可呼び出すまでゼロ
user-invocable: false不可可説明は常時／呼び出しで全文

10-5. 引数と動的コンテキスト注入

引数

変数展開されるもの例
$ARGUMENTS呼び出し時の全引数/deploy staging now → staging now
$0 $1 …位置指定（＝$ARGUMENTS[N]）$0 → staging
名前付き引数フロントマターで arguments: [issue, branch] と宣言すると名前で参照できる$issue $branch
環境変数スキルの実行環境${CLAUDE_SKILL_DIR} ${CLAUDE_PROJECT_DIR} ${CLAUDE_SESSION_ID} ${CLAUDE_EFFORT}

動的コンテキスト注入 !`command`

スキル本文が Claude に渡る前にシェルコマンドが実行され、出力がその場に埋め込まれます。「Claude にコマンドを実行させる」のではなく、前処理でデータを差し込む仕組みです。

---
name: pr-summary
description: プルリクエストの変更を要約する
context: fork
agent: Explore
allowed-tools: Bash(gh *)
---

## Pull request context
- PR diff: !`gh pr diff`
- PR comments: !`gh pr view --comments`

## Your task
このプルリクエストを要約してください…

複数行なら ```! で囲んだフェンスブロックを使います。組織で禁止したい場合は設定 disableSkillShellExecution: true（管理設定で強制可能）。

10-6. スキルのライフサイクルと評価

  • 呼び出されたスキルの本文は会話に 1 メッセージとして入り、セッション中ずっと残ります。単発の手順ではなく「常時適用される指示」として書くのが正解
  • 自動コンパクション時は、直近に呼び出されたスキルが予算内で再添付されます（上限は 7-2）
  • 効果が薄れたように見えるときは、description と指示を強化するか、コンパクション後に再呼び出しします

評価（eval）の考え方

「発火したか」と「出力が期待通りか」は別問題です。両方を、スキル有効／無効のベースライン比較で測ります。skill-creator プラグインがこのループを自動化し、テストケース、隔離実行、採点、ベンチマーク、A/B 比較、説明文チューニングまで行います。

/plugin install skill-creator@claude-plugins-official

10-7. バンドルされたスキル

最初から使える公式スキル群です（設定 disableBundledSkills で無効化可能）。中身はプロンプトなので、挙動を確認しながら自作の参考にできます。

スキル役割
/doctorインストール・設定の点検と修正。disableBundledSkills の唯一の例外で、無効化してもこれだけは使える（隠すには DISABLE_DOCTOR_COMMAND か skillOverrides の "doctor": "off"）
/code-review差分をレビューしてバグを検出（--fix で適用、ultra でクラウド多エージェントレビュー）
/batch大規模変更を 5〜30 個の単位に分割し、worktree 分離したサブエージェントで並列実行して PR を作成
/debugランタイム問題の診断
/loopプロンプトを一定間隔で繰り返す
/run / /verify / /run-skill-generatorアプリを実際に起動して変更を確認する。3 つ目は起動レシピをプロジェクト固有スキルとして記録
/claude-apiClaude API / SDK に関するリファレンス
試してみる：バンドルスキルを使う 
/code-review        # 現在の差分をレビュー（--fix で修正まで）/run                # アプリを起動して変更を確認

10-8. この章の持ち帰り

スキルは実体が Markdown 1 枚なので、今日作って今日使えます。

覚えること仕事での効き目具体的な操作
要るときだけコンテキストに差し込む常駐費は description だけ、本文は呼び出したターン以降の費用、と読める。守られないときは「コンテキストに入ったか」から疑える——スキルは文脈であって強制ではない3-9 コンテキスト、3-9 メモリ、3-9 ガードレール
まず同梱スキルを使う自作より先に、レビューも一括変更も既にある。中身はプロンプトなので自作の参考にもなる/code-review /batch /run /debug
description が命Claude が「使うべきか」を判断する唯一の材料。主要ユースケースを先頭に書くwhen_to_use と合わせて 1,536 文字で切られる
!`command` で前処理データを埋め込む「Claude に実行させる」のではなく、渡す前にデータを差し込む。往復が減って速い!`git diff HEAD`
本文は「常時適用される指示」として書く呼び出したスキルの本文はセッション中ずっと残る。単発の手順として書くと後で誤作動するSKILL.md は 500 行以下、詳細は補助ファイルへ
繰り返す手順を見つけたら即スキル化同じ手順書を 3 回貼っているなら、それはもうスキル~/.claude/skills/<name>/SKILL.md
意外と知られていない

allowed-tools が効くのは、そのスキルを呼び出したターンだけです。次のメッセージを送ると解除されます（本文はコンテキストに残るのに権限は残らない）。セッション全体で確認を省きたいなら permissions.allow に書いてください。もう一つ、~/.claude/skills/ をこの手順で初めて作ったときだけ再起動が必要です（2 つ目以降は不要）。
