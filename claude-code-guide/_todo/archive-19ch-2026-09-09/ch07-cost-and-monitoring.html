07

コストと運用監視

トークンは有限で有料です。この章は仕組み → 測る → 減らす → 異常時の順に並べています。「速く動かす」ことと「安く動かす」ことは、多くの場合同じ施策——コンテキスト管理に帰着します。

原理との対応

この章は図 1-1 のコンテキストウィンドウを「運用と観測性」の側——コスト——から見る章で、根拠は 3-9 コンテキスト（コンテキストは有限で、毎ターン丸ごと送る。先頭一致でキャッシュされる。出力は入力より高い）です。図 7-1 の「固定分＋積み上がる会話」は毎ターン丸ごと送るコンテキストそのもので、プロンプトキャッシュ（7-3）は先頭一致の再利用、言語ごとのトークン量（7-4）と計測（7-5）はコンテキストの長さを測る話、削減（7-6）と診断（7-7）は 3-9 メモリ の「縮める」「捨てる」をコストの側から見たものです。廃れないのは「短く保つ」「先頭を固定する」「出力（推論を含む）を無駄に増やさない」の 3 つが効くという構造で、変わるのは単価・プランの倍率・キャッシュの寿命・トークナイザの数値です。

7-2. 何がトークンを消費するのか

モデルはリクエスト間で何も記憶しません。ツールを使うたびに新しいリクエストが飛び、そのつど「開始時に読んだ固定分＋それまでの履歴」を丸ごと運びます。

積算の内訳

何がいつ読み込まれるかは 3-6。ここではコストの効かせ方だけを見ます。

要素いつ乗るか効かせ方
システムプロンプト＋組み込みツール（built-in tools）の定義固定分通常はキャッシュ読み。削るとキャッシュも切れる
CLAUDE.md・自動メモリ（auto memory）・スコープ無しの rules固定分短く保つ。資料はスキルへ（7-4）
スキルの説明文・MCP のツール名固定分説明文は 1 行に。使わない MCP サーバーは切る
読み込んだファイル／ツール実行結果読んだ以降ずっと調査はサブエージェント（subagent）へ。フックで前処理して絞る
拡張思考（extended thinking）の思考トークン有効なターン出力トークンとして課金。努力レベル（effort level）を作業に合わせる
コンパクション（compaction）/compact・自動圧縮のたび要約の生成が出力コスト。入力側は既存キャッシュを読むので再処理はされない。タスクの切れ目に自分で実行する
やり直し・手戻り方向を間違えたとき最大の変動費。プランモード（plan mode）と早期の軌道修正
コンパクションは「リセット」ではない

会話は要約に縮みますが固定分は残ります。CLAUDE.md と自動メモリはディスクから再注入され、呼び出し済みのスキル本文も予算内（1 スキル 5,000・合計 25,000 トークン）で再添付されます。ゼロから始めたいなら /clear です。

単価の構造 — キャッシュ読みは入力の 1/10

モデル入力キャッシュ書き込み（5分）キャッシュ読み出し出力
Claude Opus 5$5$6.25$0.50$25
Claude Sonnet 5$2$2.50$0.20$10
Claude Haiku 4.5$1$1.25$0.10$5
高速モード（Opus 5 / 4.8）$10——$50

100 万トークンあたり・2026 年 8 月時点。キャッシュ読みは入力の 1 割、出力は入力の 5 倍。つまり効くのは「キャッシュに乗せること」と「出力（思考を含む）を無駄に増やさないこと」です。

単価もモデル名も変わりますが、「出力は入力より高い」「キャッシュに乗った入力は乗らない入力より安い」という構造は変わりません（3-9 コンテキスト）。数値を覚えるより、この 2 つの不等号を覚えてください。

会話の外でも消費される

対象影響
背景処理（会話要約、/usage 等）小さい。公式の目安はセッションあたり $0.04 未満
サブエージェント（subagent）自前のコンテキストとキャッシュを持つ。大量のファイル読みが親に載らないため合計では安くなることが多い
エージェントチーム（agent teams）各メンバーが独立した Claude インスタンス。消費はメンバー数にほぼ比例し、終了するまで消費し続ける。ルーティン作業なら単一セッションのほうが安い

7-3. プロンプトキャッシュ（prompt caching）

キャッシュを壊す操作をタスクの途中で行うと、そのターンだけ約 10 倍の入力コストを払います。総消費を左右する最大の変数です。

3 層のプレフィックス一致

API はリクエストの先頭（プレフィックス）を直前の処理内容と照合します。前方に 1 箇所でも変化があると、それ以降は全て再計算されます。

層内容変わるとき
システムプロンプト中核の指示、ツール定義、出力スタイル（output style）ロードされるツール定義が変わる、Claude Code がアップグレードされる
プロジェクトコンテキストCLAUDE.md、自動メモリ、スコープ無しの rulesセッション開始、/clear、/compact の後
会話発言、応答、ツール結果毎ターン

加えて、プロンプト本文ではないのにキャッシュキーに含まれるものが 2 つ——モデルと努力レベル（effort level）です。

キャッシュを壊す操作／保つ操作

壊す
タスクの途中では避ける

モデル切替（/model）／努力レベル変更（/effort）／高速モードの有効化（/fast）／ツール全体の deny 追加／/compact／Claude Code のアップグレード

MCP サーバーの接続・切断とプラグインの切替は壊しません。ツール検索で定義が遅延ロードされる既定構成では、新しい内容が末尾に足されるだけだからです（プリフィックスに定義を載せる構成では壊します）。

保つ
いつ行ってもよい

リポジトリのファイル編集／CLAUDE.md の編集／出力スタイルの変更／権限モード（permission mode）の変更／スキル・コマンドの呼び出し／/recap／/rewind／サブエージェントの起動

「保つ」側の副作用

キャッシュを保つことは、その変更がセッション中は適用されないことと表裏です。プロジェクトルートの CLAUDE.md と出力スタイルはセッション開始時に一度だけ読まれるため、途中で編集しても効きません（反映は次の /clear か再起動から）。「CLAUDE.md を直したのに従わない」の正体はこれです（4-6）。ネストした CLAUDE.md と paths: 付き rules は後から読まれるため、ロード前の編集は反映されます。

高速モードは会話の途中でオンにすると高い

会話中に初めて有効化すると、その時点のコンテキスト全体を高速モードの未キャッシュ単価で払い直します。深いところで入れるほど高くつくため、使うならセッションの最初から。この課金は 1 会話につき 1 回で、後からオフ・オンを繰り返しても再発しません。

キャッシュの寿命（TTL）

リクエストの種別サブスクリプション（プラン内）使用量クレジット／API キー／クラウドプロバイダ
メイン会話（対話ターン、-p、Agent SDK）1 時間5 分
それ以外（サブエージェント、ワークフロー、コンパクション等）5 分（一部のヘルパーは 1 時間）5 分
  • プラン上限を超えて使用量クレジットに入ると、メイン会話も 5 分に落ちます。「上限を超えた後に急に高くつく」と感じる一因がこれです
  • どちらの場合も promptCacheTtl 設定または CLAUDE_CODE_PROMPT_CACHE_TTL 環境変数に 1h を指定すれば 1 時間を維持できます（v2.1.242 以降）。サブエージェント側は subagentPromptCacheTtl
  • キャッシュは実質的にマシンとディレクトリ単位。別ディレクトリのセッションは互いのキャッシュを読みません（worktree も別扱い）。同じディレクトリの並行セッション同士は共有します

運用の原則

  1. モデル・努力レベル・高速モードはセッション冒頭で決める。途中で変えない
  2. /compact はタスクの切れ目で自分から実行する。自動圧縮がタスクの最中に走るより安い
  3. 継続が不要なら /compact ではなく /clear。/clear は要約を生成しないぶん実質コスト 0
  4. 長い中断の後に古いセッションを --resume すると、キャッシュが切れているため最初の 1 ターンが最も高くつく

7-4. 言語ごとのトークン量

同じ内容でも、書く言語によってトークン数は変わります。まず基準値を押さえます。

1 トークンあたりの文字数

対象1 トークン ≒出典
英語の散文（公式の目安）3.5 文字Anthropic 用語集1
英語の散文（Claude 4.7 実測）3.60 文字実測2
TypeScript コード（Claude 4.7 実測）2.69 文字実測2

コードは散文より約 3 割トークン効率が悪い——記号・インデント・改行がそれぞれトークンを消費するためです。

表の「実測」は第三者による非公式の計測で、本資料の区分（0-2）では類推に当たります。手元で測った値は 7-5 にあります。

トークナイザは更新される

Claude 4.6 では英語 4.33 文字／TypeScript 3.66 文字でした。4.7 以降は新しいトークナイザが使われ、公式は「性能向上に寄与するもので、同じテキストで約 30% 多くのトークンを生成する」としています5。非公式の実測では散文で約 1.2 倍、コードで約 1.4 倍でした2。数値は目安として扱い、モデルを変えたら測り直してください。

同じ意味の文を書いたときの言語別トークン量

この図は参考値。固定の定数として扱わない

cl100k_base は OpenAI のトークナイザで、Claude のものではありません（Claude のものは非公開で、言語間比較の公開データがない）。比はモデル更新でも動き、4.6 → 4.7 では英語だけ密度が下がったため新しいモデルほど日本語との差は縮みます2。実際の値は 7-5 の手順で計測してください。

「日本語だから安い／高い」より、どこに書くかが効く

問題は量ではなく頻度です。会話は毎リクエストで全履歴が再送されるため、常時読み込まれる資産だけが固定費として毎ターン乗り続けます。

資産読み込まれる頻度言語の効き方
CLAUDE.md・スコープ無しの rules毎リクエスト最も効く。簡潔に。長い資料はスキルへ
スキルの description毎リクエスト（全スキル分）1 行に収める
MCP のサーバー説明毎リクエスト使わないサーバーを切る
スキル本文・参照資料呼び出したときだけ影響は小さい。日本語で書いてよい
読み込んだソースコード読んだ以降ずっと言語より「読ませすぎない」ことが効く

結論は「指示は短く、資料はオンデマンドに」。日本語で書くこと自体を避ける必要はありません。避けるべきは、常時ロードされる場所に長文を置くことです。

母語で書けば安く済む、とは限らない

中国語と英語のプロンプトを比較した研究では、3 モデル中 2 モデルで中国語のほうがトークンを多く使い、3 モデルすべてで解決率が下がりました（例：66.0% → 61.5%）4。Claude と日本語は対象外なので断定はできませんが、「非英語で書けばトークンが減る」という期待は成立しないと考えたほうが安全です（類推）。

7-5. 使用量の計測

/usage — 3 つのブロックを読み分ける

ブロック読み取れること備考
Session現セッションのモデル別トークン数（入力／出力／キャッシュ読み／キャッシュ書き）と概算コスト/clear でリセット。金額はローカルで定価から計算した概算
Prompt cache (main)リクエスト数、入力トークンのうちキャッシュから読まれた割合、ミス回数、warm / cold と TTLメイン会話のみ。サブエージェントは含まない（7-3）
プラン使用量の内訳何が消費しているかの帰属（スキル・サブエージェント・プラグイン・MCP サーバー別）、挙動フラグ（長いコンテキストやキャッシュミスが 10% 以上のとき警告）、重い /loop の一覧Pro / Max / Team / Enterprise のみ。d / w で 24 時間・7 日間を切替

使い分け

知りたいこと手段
自分がどの経路・プランで課金されているか/status
今のセッションで何にいくら使ったか/usage
コンテキストの内訳（CLAUDE.md・スキル・MCP が各何トークンか）/context
コンテキスト残量・キャッシュの温度を常時見たいステータスライン（6-6）
使用量ではなく働き方の傾向・摩擦点/insights（~/.claude/usage-data/report.html に出力）
組織のメンバー別・リアルタイムの消費OpenTelemetry（下記）
組織の採用状況・生産性の推移分析ダッシュボード（analytics dashboard・Team / Enterprise）
使用量クレジットの残高・月間支出上限を管理したい/usage-credits
組織で見るなら OpenTelemetry

ユーザー単位・セッション単位の数値を全構成で取れる唯一の方法です（Bedrock・Google Cloud・Microsoft Foundry のように Console ダッシュボードが使えない経路を含む）。トークン数、キャッシュ読み／書き、コスト、セッション数などをメトリクスとイベントとしてエクスポートできます。

契約単価がある組織は、管理設定（managed settings）の modelPricing に単価を設定すると、/usage やステータスラインの金額が定価ではなく実際の請求額に一致します（v2.1.242 以降）。

試してみる：まず見る 3 つ 
/status     # ログイン方法とアカウント種別（どの経路で課金されるか）/usage      # セッション・キャッシュ・プラン内訳（d / w で期間切替）/context    # コンテキストの内訳/insights   # 働き方のレポートを HTML で出力

実際に測ってみる — 言語による差を確かめる

小さな作業を英語と日本語でやらせ、入力・思考・出力のトークンをそれぞれ測ります。API キーは不要です。

先に環境を揃える — ここを外すと比較にならない

そのまま計測すると、自分の設定が結果を汚染します。CLAUDE.md に「出力は日本語で」と書いてあれば英語版でも日本語が返り、大量のコンテキストを積んでいれば固定分が膨らんで差が埋もれます。

方法無効になるもの使いどころ
--safe-modeCLAUDE.md・自動メモリ・スキル・プラグイン・フック・MCP・カスタムコマンド・出力スタイル・LSP などほぼ全部計測はこれ。素の状態を基準にできる
CLAUDE_CODE_DISABLE_CLAUDE_MDS=1CLAUDE.md（ユーザー・プロジェクト）と自動メモリのみスキルや MCP は載せたまま比べたいとき
--baresafe-mode 相当＋ツールも最小限認証が ANTHROPIC_API_KEY 限定になるためサブスクリプションでは使えない

どちらも計測のときだけ使ってください。通常の作業で付けると、指示もスキルも効かなくなります。

手順 1：作業内容を英語版と日本語版で用意する 
mkdir -p /tmp/tok && cd /tmp/tokcat > task_en.txt <<'EOF'
Answer in English. Do not use any tools.

def last_n(items, n):
    return items[len(items) - n - 1:]

This should return the last n elements, but it returns n+1 elements.
Explain the bug in two or three sentences and show the corrected function.
EOFcat > task_ja.txt <<'EOF'
日本語で答えてください。ツールは使わないでください。

def last_n(items, n):
    return items[len(items) - n - 1:]

これは末尾 n 件を返すはずですが、n+1 件返します。
バグの原因を 2〜3 文で説明し、修正版の関数を示してください。
EOF

オフバイワンのバグを直させる小さな作業です。考えて、説明して、コードを書く——実際の使い方に近く、かつ数百トークンで終わります。出力言語はプロンプト側で明示しているので、設定に左右されません。

手順 2：基準と 2 パターンを計測する 
measure() {
  DISABLE_PROMPT_CACHING=1 claude -p --safe-mode --model haiku --output-format json --max-turns 1 \
  | python3 -c 'import json,sys; u=json.load(sys.stdin)["usage"]; print("in",u["input_tokens"],"out",u["output_tokens"],"think",u["output_tokens_details"]["thinking_tokens"])'
}

printf 'base: '; echo ok | measure
printf 'en:   '; measure < task_en.txt
printf 'ja:   '; measure < task_ja.txt

フラグを変数にまとめて $M のように渡すと、zsh では単語分割されず 1 個の引数として扱われて失敗します。上のように関数にするのが確実です。

出力例（Haiku 4.5・答え合わせ用の一例・実測）：

base: in 16101 out 128 think 108
en:   in 16170 out 588 think 425
ja:   in 16200 out 680 think 469
手順 3：差を取る

base はシステムプロンプトなどの固定分です。入力はこれを引くと、プロンプト本体のトークン数が出ます。

                  英語   日本語     比
入力（プロンプト）    69     99    1.43 倍   ← 16170-16101 / 16200-16101
思考                425    469    1.10 倍
回答本文            163    211    1.29 倍   ← 出力合計 - 思考
出力の合計          588    680    1.16 倍

この例で最も大きいのは思考トークンで、出力全体の約 7 割を占めています。プロンプト本体の差（1.43 倍）がそのまま総額に効くわけではない——というのが、テキストを読ませるだけの計測では見えない点です。

この数値の位置づけ

上は1 つの小さな作業を 1 回測っただけの例で、言語間の比を一般化できる規模の検証ではありません。手順が正しく動いているかの答え合わせとして使ってください。判断に使う数値は、自分がよく出すプロンプトで測り直します。

また入力トークンは毎回同じ値になりますが、思考と出力は同じプロンプトでもばらつきます（別の実行では英語 out 474 / think 348、日本語 out 598 / think 429 でした）。出力側を見るときは 3 回ほど走らせて均してください。

思考トークンが 0 になるモデル・設定もあります。上の例は Haiku 4.5 のもので、別のモデルでは think 0 になり、言語差も別の出方をしました。使うモデルを揃えて比べてください。

計測時の注意
  • DISABLE_PROMPT_CACHING=1 が要点です。付けないと入力の大半が cache_creation_input_tokens に回り、input_tokens が実態を映しません
  • そのぶん毎回全文が未キャッシュで処理されます。1 回あたり 1〜4 万トークンかかるので、確認したいときだけ実行してください
  • 比べたいモデルを --model sonnet のように明示します。モデルが違えば結果も変わります。ただし系列の違うモデル同士を比べても、差がトークナイザ由来かは切り分けられません
  • 同じディレクトリで連続して実行してください。作業ディレクトリはシステムプロンプトに埋め込まれるため、ディレクトリが違うと base も変わります
  • 新しいディレクトリでの初回実行は、フォルダを信頼するか尋ねられて空の結果になることがあります。その場合は同じコマンドをもう一度実行してください
おまけ：自分の CLAUDE.md がいくら掛かっているか

同じプロンプトを、設定ありとなしで測って引き算します。毎リクエスト乗る固定費がそのまま出ます。

usage() { python3 -c 'import json,sys; print("in", json.load(sys.stdin)["usage"]["input_tokens"])'; }

printf '通常          : '; echo ok | DISABLE_PROMPT_CACHING=1 claude -p --output-format json --max-turns 1 | usage
printf 'CLAUDE.md なし: '; echo ok | CLAUDE_CODE_DISABLE_CLAUDE_MDS=1 DISABLE_PROMPT_CACHING=1 claude -p --output-format json --max-turns 1 | usage
printf 'safe-mode     : '; echo ok | DISABLE_PROMPT_CACHING=1 claude -p --safe-mode --output-format json --max-turns 1 | usage

出力例（ある環境での一例・実測。数値は人によって大きく違います）：

通常          : in 40488
CLAUDE.md なし: in 23420   ← CLAUDE.md・rules・自動メモリで 17,068
safe-mode     : in 16134   ← さらにスキル・MCP などで 7,286

この例では CLAUDE.md 系だけで 17,000 トークン超が毎リクエストに乗っていました。ここが大きいなら、言語を英語に寄せるよりまず量を削るほうが効きます。内訳は /context で分類別に確認できます。

7-6. 使用量の削減

効果の大きい順に 5 系統。上 2 つが金額への効き目が大きく、下にいくほど地道な削減です。

効き目系統具体策
★★★手戻りを減らす
最大の変動費		指示の精度・プランモード・早期の軌道修正・検証手段の付与が効く。具体的な型は 5-1 と 5-5 に集約
★★★キャッシュを壊さないモデル・努力レベル・高速モードはセッション冒頭で固定する／/compact はタスクの切れ目に自分から実行（→ 7-3）
★★コンテキストを小さく保つタスクの切れ目で /clear（後で戻るなら先に /rename）／/compact に焦点を指定（CLAUDE.md の # Compact instructions で既定化できる）／/autocompact 500k で発火点を早める／冗長な調査はサブエージェントに委譲
★★モデルと推論設定単純作業に Opus を使わない。Sonnet は Opus の約 4 割、Haiku は約 2 割の単価（7-2）／/effort を下げる（思考は出力として課金）。ただしタスク途中では変えない／固定予算のモデルは MAX_THINKING_TOKENS／高速モードはコストが問題ならオフ（入力・出力とも 2 倍）
★処理を外に出す決まりきった処理はフックやスクリプトへ（1 万行のログをフックで ERROR 行だけに絞れば数万トークンが数百に）／CLAUDE.md の参照資料をスキルへ移す＝固定費が変動費になる／使っていない MCP を切る（gh・aws・gcloud が使えるならそちらが安い）／型付き言語はコードインテリジェンスでファイル全読みを定義ジャンプに置き換える

7-7. 想定より多いときの診断

何時間も開いたままのセッションは、体感の作業量に比べてプラン上限を大きく消費します。「席を外していたのに減っている」には、はっきりした原因があります。

原因何が起きているか対処
長いコンテキスト毎リクエストで全会話を送るタスクの切れ目で /clear。調査はサブエージェントへ
キャッシュミスキャッシュ寿命を超える中断の後、最初の 1 通が全コンテキストを再処理する長い中断の前に /clear。再開は要約から
スケジュールタスク/loop などがアイドル中も間隔ごとに発火する不要になったループを止める
クロスセッションメッセージ他セッションからのメッセージがアイドル時に新しいターンとして配送される受信を保留する設定にする
/goal のチェックインバックグラウンド作業がゴールを待たせている間、アイドルでも評価ターンが起きる不要になったゴールを /goal clear
エージェントチームメイト各メンバーが終了するまで消費し続ける終わったメンバーを止める
コンパクション要約の生成に出力トークンを使い、直後に会話キャッシュを作り直す継続が不要なら /clear
原因の特定は /usage が早い

Pro / Max / Team / Enterprise では、/usage が直近の使用量の 10% 以上を占める挙動に自動でフラグを立て、対処のヒントを添えます。上の表を上から疑うより先に見てください。

7-8. この章の持ち帰り

コスト削減は精神論ではありません。効き目の順に 3 つやれば大半が片づきます。

覚えること仕事での効き目具体的な操作
コンテキストは有限で、毎ターン丸ごと送る。コストはその長さ × 往復回数 ＋ 出力単価やプランが改定されても、「短く保つ」「先頭を固定する」「出力を増やさない」の 3 つが効くことは変わらない。新しい課金項目も、固定分・積み上がり・出力のどれかに位置づけられる3-9 コンテキスト のコストの構造
モデル・努力レベル・高速モードは冒頭で固定途中で変えるとキャッシュが壊れ、そのターンだけ入力が約 10 倍になる/model /effort は作業開始前に
継続不要なら /compact ではなく /clear/clear は要約を生成しないぶん実質コスト 0。惰性で /compact を打たない戻る予定があるなら先に /rename
キャッシュ読みは入力の 1/10、出力は入力の 5 倍「キャッシュに乗せる」「出力（思考を含む）を無駄に増やさない」の 2 点に集約できる単純作業に Opus と高い /effort を使わない
原因調査は /usage が最速直近の 10% 以上を占める挙動に自動でフラグが立つ。表を上から疑うより速い/usage（d / w で期間切替）
自分の固定費を一度測る毎リクエストに乗る CLAUDE.md・スキル・MCP の総量が分かる。削る優先度が決まるCLAUDE_CODE_DISABLE_CLAUDE_MDS=1 との差分
意外と知られていない

高速モードを会話の途中で有効にすると、その時点のコンテキスト全体を未キャッシュ単価で払い直します。深いところで入れるほど高くつくので、使うならセッションの最初からです（課金は 1 会話につき 1 回）。もう一つ、プロンプトキャッシュは実質的にディレクトリ単位で、worktree は別扱いのため互いのキャッシュを読みません。並列化の隠れたコストです。
