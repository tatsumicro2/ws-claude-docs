study plan · 5 weeks × 10–15 min

Claude Code 深掘り 5 週

網羅ではなく、「なぜそう動くか」を 1 つの原理で貫いて、翌日の実務で使える操作まで落とす 5 回。聞き手は Claude を触ったことのあるエンジニアなので、機能紹介は省き、仕組みと使い方の因果に時間を使う。

聞き手 エンジニア（Claude の基礎知識あり） 1 回 12〜15 分 出典 claude-code-guide/（公式ドキュメント準拠）

全体の貫き方

毎回 1 つの原理 → その原理が生む「よくある症状」 → 症状を消す操作 → デモ の順で話す。原理はすべて「LLM は記憶も副作用も持たず、有限のコンテキストを毎ターン丸ごと送り、ツールは選ぶだけで実行しない」から派生するので、5 回を通して同じ絵（下の図）に部品が足されていく形になる。

week 1ループとコンテキスト「さっき言ったよね」が通じない理由 week 2記憶と指示（CLAUDE.md）書いたのに守られない理由 week 3コストとキャッシュ同じ作業なのに高い日がある理由 week 4Subagents と Skills分けると安く・正確になる理由 week 5Hooks と権限お願いを強制に変える唯一の層
時間枠やること
0–1 分つかみ全員が一度は踏んだ「症状」を 1 つ出す（「CLAUDE.md を直したのに従わない」など）
1–4 分原理図を 1 枚見せて、その症状が仕様である理由を説明する
4–9 分説明原理から出てくる「効く操作」を 3〜4 個。数値は資料の実測値だけ使う
9–13 分デモターミナルで 1 つだけ実演。コピペで再現できる形にする
13–14 分持ち帰り「明日やること 1 つ」と「意外と知られていない事実 1 つ」で締める
WEEK1

エージェントループとコンテキストウィンドウ

つかみ：「さっき言ったよね」が通じないのはなぜか。 覚えているように見えるのは、毎回これまでの全部を渡し直しているから。

説明内容 4–9 分

  • 状態はコンテキストの中身だけ。システムプロンプト・CLAUDE.md・会話・読んだファイル・コマンド出力が毎ターンまとめて送られる。「覚えている」の正体は JSONL を読み直していること。
  • 有限なので消える。上限に近づくと古いツール出力から削られ、次に会話が要約される。要約後、元の文言は無い。
  • ツールは「選ぶだけ」。実行の直前に人・ルール・フックが割り込める。ガードレールの居場所はここ 1 か所（week 5 の伏線）。
  • ループが収束する条件は「周回ごとに合否がコンテキストに入ること」。テスト・型検査・Lint の合否が次の周回の入力になる。合否が返らない仕事では「それらしいもの」を出して止まる。だから「テストを先に書いて」が効く。
  • 2 回失敗したら /clear。失敗案が積み上がったコンテキストは、続けても精度が上がらない。学んだことを織り込んで最初から依頼し直すほうが速い。

実用例：/context で「今なにを送っているか」を見る

1普段のプロジェクトで claude を起動し、何もせず /context。固定分（システムプロンプト・ツール定義・CLAUDE.md・MCP）が何トークンか読み上げる。
2大きめのログを cat させてからもう一度 /context。積み上がりを見せる。
3「Bash の出力は約 30,000 文字で切られ、超えた分はファイルに退避してパスだけ返る」を実演。長いログは grep で絞ってから渡すほうが速くて安い、に着地。
# 落とし穴の再現：30,000 文字を超える出力
seq 1 20000 | awk '{print "line " $1 " ..."}'
# 正しい渡し方
grep -n "ERROR" app.log | tail -50
持ち帰り

明日やること：遅い・高い・指示が効かない、の 3 つとも最初に /context を見る癖をつける。

意外と知られていない：Bash はコマンドごとに別プロセス。export や venv の有効化は次のコマンドに引き継がれない。「環境変数を設定したのに効かない」の正体。

WEEK2

記憶と指示 — CLAUDE.md・rules・自動メモリ

つかみ：「CLAUDE.md を直したのに従わない」。不具合ではなく仕様。永続化は文脈であって強制ではなく、しかもセッション開始時に一度しか読まれない。

説明内容 4–9 分

  • 2 系統ある。人が書く CLAUDE.md / rules と、モデルが書く自動メモリ。どちらも「次のセッションの先頭に読み込むファイル」で、原理は同じ。
  • 永続化は文脈であって強制ではない。CLAUDE.md は「お願い」。守られる確率を上げることはできるが 100% にはならない。絶対に守らせたい規則は week 5 の層へ。
  • 短いほど効く。目安は 200 行以下。「適切に」ではなく「インデントは 2 スペース」のように検証可能な粒度で書く。長いほど重要な行がノイズに埋もれ、しかも毎ターンの固定費になる。
  • 常時ロードを rules に逃がす。.claude/rules/*.md に paths: を付ければ、該当ファイルを触ったときだけ読まれる。固定費が下がる。
  • 診断は「読まれたか」から。/context の Memory files に出ていないファイルは、いくら書き直しても効かない。@ インポートの承認を一度でも拒否すると以後ダイアログは出ず、無効のまま。

実用例：肥大した CLAUDE.md を rules に分割する

1wc -l CLAUDE.md で行数を見せる。200 行超なら削る対象。
2フロントエンド限定の規約を .claude/rules/web.md に移し、paths: で限定する。
3/clear してから /context。固定分が減っていることと、src/components/ を触ったときだけ rules が Memory files に現れることを見せる。
# .claude/rules/web.md
---
paths:
  - "src/components/**"
---
- コンポーネントは PascalCase、CSS クラスは kebab-case
- アニメーションは transform / opacity のみ
4レビューで同じ指摘を 2 回したら、その場で # インデントは 2 スペース と打って追記する動きも見せる。
持ち帰り

明日やること：自分のプロジェクトの CLAUDE.md を /init でたたき台を作り、そこから「削って育てる」。同じ指摘を 2 回したら追記。

意外と知られていない：ルートの CLAUDE.md はセッション開始時に一度だけ読まれる。作業中の編集はそのセッションに反映されず、次の /clear か再起動から効く。ネストした CLAUDE.md と paths: 付き rules は後から読まれるので、ロード前の編集は反映される。

WEEK3

コストの構造とプロンプトキャッシュ

つかみ：「同じ作業をしたのに、やけに高い日がある」。金額を決めるのは単価表ではなく、固定分の大きさ × 往復回数 ＋ 出力、そしてキャッシュが切れた回数。

説明内容 4–9 分

  • 覚えるのは 2 つの不等号。キャッシュ読みは入力の 1/10、出力は入力の 5 倍。単価もモデル名も変わるが、この構造は変わらない。効くのは「キャッシュに乗せる」「出力（思考を含む）を無駄に増やさない」。
  • キャッシュは先頭一致。前方に 1 か所でも変化があると、それ以降は全部再計算。プロンプト本文でないのにキャッシュキーに入るものが 2 つ：モデルと努力レベル。
  • 壊す操作：/model・/effort・/fast・ツール全体の deny 追加・/compact・アップグレード。保つ操作：ファイル編集・CLAUDE.md 編集・権限モード変更・スキル呼び出し・サブエージェント起動。MCP の接続・切断も既定構成では壊さない。
  • /compact と /clear の使い分け。/compact は要約の生成が出力コスト。継続が不要なら /clear のほうが実質コスト 0。タスクの切れ目で自分から打つほうが、作業の最中に自動圧縮が走るより安い。
  • キャッシュは実質ディレクトリ単位。worktree は別扱いで互いのキャッシュを読まない。並列化の隠れたコスト。

実用例：自分の固定費を一度測る

1普段どおり起動して /context。固定分の合計を控える。
2CLAUDE.md を外して起動し、差分を見る。
CLAUDE_CODE_DISABLE_CLAUDE_MDS=1 claude
# → /context で固定分を比較
3/mcp でサーバーごとのトークンコストを見せ、使っていないものを切る判断を数字でする。
4/usage（d / w で期間切替）。直近の 10% 以上を占める挙動に自動でフラグが立つので、原因調査はここが最速。
持ち帰り

明日やること：モデル・努力レベル・高速モードはセッション冒頭で決めて、途中で変えない。単純作業に Opus と高い /effort を使わない。

意外と知られていない：高速モードを会話の途中で有効にすると、その時点のコンテキスト全体を未キャッシュ単価で払い直す。深いところで入れるほど高くつくので、使うなら最初から（課金は 1 会話につき 1 回）。

WEEK4

Subagents と Skills — 分ける・要るときだけ差し込む

つかみ：「調査を頼んだら数百ファイル読んで、本題の会話が濁った」。サブエージェントの本体価値は「並列で速い」ではなく「メインを汚さない」。

説明内容 4–9 分

  • サブエージェント＝別コンテキストで回し、要約だけ戻す。親が安く速くなる理由と、「途中で何をしたか」を後から親に聞いても分からない理由が同じ原理。過程が要る仕事は委譲しない。
  • 組み込みの Explore は軽い。読み取り専用で、CLAUDE.md も git status も読まない。探索の初手に最適。
  • Writer と Reviewer を分ける。実装に至った思考を知らないレビュアーは確証バイアスが入りにくい。/code-review はこれを標準化したもの。ただし「欠落を探せ」と言われたレビュアーは健全な実装でも必ず何か報告するので、正確性か明示要件に関わるものだけ対応する。
  • スキルは description が命。Claude が「使うべきか」を判断する唯一の材料。主要ユースケースを先頭に書く。when_to_use と合わせて 1,536 文字で切られる。
  • 本文は「常時適用される指示」として書く。呼び出したスキルの本文はセッション中ずっと残る。単発の手順として書くと後で誤作動する。!`command` で前処理データを渡す前に埋め込むと往復が減る。

実用例：敵対的レビューをスキル化する

1ファイルを作る前に、その場でサブエージェントの挙動を確かめる。
claude --agents '{"reviewer":{"description":"差分だけを見て欠陥を探す","prompt":"実装の経緯は知らない前提で、正確性と明示要件に関わる問題だけ報告して","tools":["Read","Grep","Glob","Bash"]}}'
2使えると分かったらスキルに落とす。!`git diff HEAD` で差分を先に埋め込み、レビュアーへ委譲する手順を本文に書く。
# ~/.claude/skills/adversarial-review/SKILL.md
---
name: adversarial-review
description: 実装者と別のコンテキストで差分だけをレビューする。PR 前・コミット前に使う
---
次の差分を reviewer サブエージェントに渡し、
正確性と明示要件に関わる指摘だけを表にして返して。
!`git diff HEAD`
3/context で「レビュー中に読んだファイルが親に載っていない」ことを見せて締める。
持ち帰り

明日やること：「調査して」は必ず「サブエージェントで調査して」に言い換える。同じ手順書を 3 回貼っていたら、それはもうスキル。

意外と知られていない：スキルの allowed-tools が効くのは呼び出したターンだけ。次のメッセージで解除される（本文は残るのに権限は残らない）。もう一つ、日本語版ドキュメントはサブエージェントのネスト深さを「5 階層・設定不可」としているが、英語版では既定 3 階層・環境変数で変更可。同時実行 20 の上限は日本語版に記載がない。

WEEK5

Hooks と権限 — お願いを強制に変える唯一の層

つかみ：「.env を触るなと CLAUDE.md に書いたのに触った」。CLAUDE.md は確率的な「お願い」。守られないと困る規則は、ハーネスが決定論的に止める層に置く。

説明内容 4–9 分

  • 置き場所は一意に決まる。守られなければ困る規則は フック / deny ルール（決定論的）。守られると嬉しい程度の指針は CLAUDE.md（確率的）。
  • 評価順は deny → ask → allow。ルールの詳細度は順序を変えない。Bash(aws *) を deny しつつ Bash(aws s3 ls) だけ allow、は書けない。権限設計でいちばん多いつまずき。
  • 安全なコマンドは許可リストへ。Bash(npm test:*) などを /permissions から足す。プロンプト疲れが消え、確認の判断力を危険な操作に温存できる。
  • フックの型：exit 2 でブロック、stderr がフィードバック。禁止するだけでなく「なぜ駄目か」を伝えて別の手を打たせる。編集対象のパスを渡す環境変数は無いので、stdin の JSON から jq で取る。
  • Bash 経由の変更は PostToolUse で捕まらない。監査目的ならターンごとに作業ツリーを走査する Stop フックを併用する。

実用例：.env 保護と保存時整形を 5 分で入れる

1/hooks から対話的に追加する（settings.local.json を手で上書きして壊さないため）。
2PreToolUse に Write|Edit でマッチさせ、.env と本番設定への書き込みを拒否する。
#!/bin/sh
f=$(jq -r '.tool_input.file_path')
case "$f" in
  *.env|*/config/production.*)
    echo "保護ファイルです。.env.example を編集してください" >&2
    exit 2 ;;
esac
3PostToolUse に同じマッチで prettier --write "$f"。以後、頼まなくても必ず整形される。
4「.env に API キーを追記して」と頼んで、拒否理由を受けて Claude が .env.example に切り替える様子を見せる。
持ち帰り

明日やること：CLAUDE.md の「絶対に〜するな」を全部拾い出し、フックか deny ルールに移す。整形・Lint・通知はフックへ。

意外と知られていない：フックは 5 種類あり、シェルコマンドだけではない。command のほか http・mcp_tool・prompt（LLM に判定させる）・agent（サブエージェントで検証）。「機械的には判定できないが必ずチェックしたい」ものを prompt フックに置ける。なお exit 2 と構造化 JSON の併用はできない。

採らなかった候補と、差し替えるなら

5 週で 1 本の筋を通すために外したもの。聞き手の関心が明らかに偏っているなら、week 4 か 5 と入れ替える。

候補外した理由入れるなら
MCP原理上は week 1 の「ツール使用」そのもので、独立回にすると重複が多い。公式も「先に CLI で足りないか疑え」week 4 に 3 分足す：/mcp のトークン表示と「MCP は能力、Skill は使う知識」
非対話モード・CI/CD「人が周回に入らないループ」で、week 1 と 5 の応用。前提として権限設計（week 5）が要るweek 5 と入れ替え：claude -p --bare --allowedTools ＋ --output-format json --json-schema で PR 要約を CI に載せるデモ
並列作業・worktree・エージェントチームコストが人数に比例し、ルーティン作業なら単一セッションのほうが安い。深掘りより「使いどころの判断」の話になるweek 4 の末尾に 2 分：claude --worktree と「worktree はキャッシュを共有しない」
Plugins・マーケットプレイス配布の仕組みで、仕組みの理解というより運用の話。個人利用の段階では効き目が薄いチーム展開が決まった時点で番外編に

数値・仕様はすべて claude-code-guide/（公式ドキュメント準拠、日本語版が古い箇所は英語版に従う）から。単価や上限値は改定されるので、発表前に該当節で最新を確認する。
