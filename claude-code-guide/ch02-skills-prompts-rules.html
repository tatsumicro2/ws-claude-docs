02

スキル・プロンプト・ルール

Claude に「何をどうやらせるか」を伝える手段は 3 つあります。その場のプロンプト、毎回読まれる CLAUDE.md とルール、必要になったときだけ読まれるスキルです。どれもコンテキストウィンドウに文章を置く行為で、違うのは「誰が書くか」と「いつ入るか」だけ。それを押さえると、何をどこに書けばよいかが決まります。

原理との対応

この章は図 1-1 の長期メモリのうち人が書く部分と、ループへの入口であるプロンプトの実装です。根拠は 3-6 メモリ の「外に残す」と 3-6 コンテキスト の「毎ターン丸ごと送る」。CLAUDE.md・ルール・スキル・自動メモリは、どれもコンテキストの先頭か途中に足されるだけで、モデルへの強制力はありません。だから 2-8 の診断は「読み込まれているか」から始まり、絶対に守らせたいことはハーネス側（フック・deny ルール。5 章）へ逃がします。廃れないのは「永続化は文脈であって強制ではない」「起動時に読んだ分は毎ターンの固定費」の 2 点で、置き場所のパス・読み込み順・行数の上限は変わります。

2-1. 指示を与える 3 つの経路

指示はどれも最終的にコンテキストウィンドウに入ります。違いは誰が書き、いつ入り、どれだけ残るかです。

経路誰が書くかいつコンテキストに入るか向いているもの本章
プロンプトあなた（その場で）送った瞬間。会話として残る今回のタスクの目的・制約・対象ファイル2-5
CLAUDE.mdあなた（ファイル）毎セッションの開始時に全文。毎ターン送られる固定費プロジェクトの規約・コマンド・毎回守ってほしいこと2-2
ルール（.claude/rules/）あなた（ファイル）paths なしは起動時。paths ありは一致するファイルを触ったとき特定のディレクトリや拡張子にだけ効く規約2-3
スキル（SKILL.md）あなた（ファイル）起動時は説明文だけ。本文は呼び出したとき、以後セッション中ずっと残る繰り返す手順・チェックリスト・長い参照資料2-6
自動メモリClaude毎セッションの開始時に冒頭のみClaude が会話から学んだあなたの好みや決定事項2-4
原則

5 つとも Claude に読ませるコンテキストであり、遵守は保証されません。「絶対に守らせたい」ことは PreToolUse フックか権限の deny ルールで強制してください（5-4・5-6）。CLAUDE.md に「.env を触るな」と書くのは依頼、フックで書き込みをブロックするのは強制です。

どこに書くかの判断

  • 今回だけの話ならプロンプト。同じ説明を 2 回打ったら CLAUDE.md に移す
  • CLAUDE.md の一節が「事実」ではなく「手順」に育ってきたらスキルに切り出す。呼ばれるまでコンテキストを食わない
  • 一部のファイルにしか関係ない規約はルールに paths を付けて逃がす。毎ターンの固定費が下がる
  • チームで共有すべきことは自動メモリに任せず、コミットされる CLAUDE.md に明示的に書く

2-3. rules によるパス限定

CLAUDE.md が膨らんできたら、.claude/rules/ にトピック別ファイルとして分割します。paths を指定すると一致するファイルを触ったときだけ読み込まれ、コンテキストを節約できます。

your-project/
└── .claude/
    ├── CLAUDE.md            # 常時読み込まれるコア規約
    └── rules/
        ├── code-style.md
        ├── testing.md
        └── api-design.md    # paths 指定で条件付き読み込み
---
paths:
  - "src/api/**/*.ts"
  - "lib/**/*.{ts,tsx}"
---

# API 開発ルール
- すべてのエンドポイントに入力検証を入れる
- 標準のエラーレスポンス形式を使う
  • paths なしのルールは .claude/CLAUDE.md と同じ優先度で起動時に読み込まれる
  • .md は再帰的に検出されるので rules/frontend/ のような整理も可能。シンボリックリンクにも対応し、複数リポジトリで共通ルールセットを共有できる
  • ユーザーレベルは ~/.claude/rules/（プロジェクトルールより先に読み込まれる＝プロジェクト側が優先）
試してみる：パス限定ルールを作る 
mkdir -p .claude/rules && cat > .claude/rules/testing.md <<'EOF'
---
paths: ["**/*.test.ts"]
---
- テストは Arrange-Act-Assert の順で書く
EOF

次に *.test.ts を触らせると、このルールだけが追加で読み込まれます。

2-4. 自動メモリ（auto memory）

CLAUDE.md があなたの書く記憶なら、自動メモリは Claude が自分で書く記憶です。会話から学んだことをプレーンな Markdown に残し、次のセッションの先頭に読み込みます。

項目内容
何が保存されるか4 種類（フロントマターの type）。user＝あなたの役割・専門・作業の好み／feedback＝あなたの指摘と、確定した進め方／project＝進行中の作業・期限・コードや git 履歴から導けない決定／reference＝Issue トラッカー等、プロジェクト外の情報の在り処
保存されないものコードベースから導けること（アーキテクチャ、ファイルパス、デバッグの修正内容）と、CLAUDE.md に既に書いてあること。毎セッション必ず保存するわけでもない
既定と無効化既定で有効。/memory のトグル、autoMemoryEnabled: false、CLAUDE_CODE_DISABLE_AUTO_MEMORY=1
保存場所と構成~/.claude/projects/<project>/memory/。MEMORY.md がインデックスで、詳細は個別トピックファイルに分離される。マシンローカルで他マシンとは共有されず、コミットもされない
起動時に読まれる範囲MEMORY.md の冒頭のみ（先頭 200 行 / 25KB）。トピックファイルはオンデマンド
使い分け

「今後は npm ではなく pnpm を使って」と会話で頼むと自動メモリに保存されます。チームで共有すべきルールは自動メモリではなく CLAUDE.md に明示的に書いてください。# プレフィックスでその場からメモリに追記できます。

2-5. プロンプトの技法

公式のベストプラクティスから、対話の技法に関わる部分をまとめます。根拠は 1 つで、エージェントループは機械的な合否がコンテキストに入る領域でだけ収束する（3-6 ループ）。この節の技法はすべて、合否をコンテキストに入れる工夫か、外れた周回を減らす工夫です。

3 つの基本原則

01
検証手段を与える

テスト、ビルド、比較用スクリーンショット。Claude が自分でチェックできるかどうかが、「見張るセッション」と「任せられるセッション」を分ける。

02
探索 → 計画 → 実装

調査と実装を分けると、間違った問題を解くことを防げる。ただし小さく明確な修正に Plan Mode は不要（オーバーヘッドになる）。

03
具体的なコンテキストを渡す

対象ファイル、制約、参考にすべき既存パターンを明示する。最初のプロンプトの精度が、後の手戻りを決める。

チェックアウトフローが、期限切れカードのユーザーで壊れています。
src/payments/ を、特にトークン更新まわりを中心に確認してください。
まず失敗するテストを書いて、その後で修正してください。

対話の技法

  • 会話として扱う：完璧なプロンプトは不要。まず投げて、そこから修正する
  • 中断して操舵する：Esc で即停止、あるいは実行中に補足を送る
  • 委譲する（指示しすぎない）：読むファイルや実行コマンドを逐一指定せず、目的と制約を伝える
  • コードベースへの質問に使う：「ロギングはどう動く？」「なぜ 333 行目で foo() を呼ぶ？」。オンボーディングに極めて有効
  • 逆にインタビューさせる：大きめの機能では AskUserQuestion で Claude に質問させ、仕様を SPEC.md に落としてから、新しいセッションで実装させる
[brief description] を作りたい。AskUserQuestion ツールで詳しくインタビューしてください。
技術実装、UI/UX、エッジケース、懸念、トレードオフについて。
自明な質問は不要。私が見落としていそうな難所を掘ってください。
一通り終わったら SPEC.md に完全な仕様を書いてください。

よくある失敗パターン

アンチパターン症状対処
キッチンシンク・セッション1 つのセッションで無関係な話題を行き来し、コンテキストが雑多になるタスクの切れ目で /clear（4-3）
修正の連鎖間違い → 修正 → まだ間違い、の繰り返しで失敗案が蓄積2 回失敗したら /clear して初期プロンプトを書き直す
過剰な CLAUDE.md長すぎて重要なルールがノイズに埋もれる容赦なく削る。守らせたいものはフックへ
信頼して検証しないそれらしい実装だがエッジケースを落としている常に検証手段（テスト・スクリプト・スクショ）を与える
無限探索スコープなしの「調査して」で数百ファイルを読む対象ディレクトリと問いを絞る
最後に

公式ドキュメント自身が述べているとおり、これらは固定ルールではありません。うまくいったときに何をしたかを観察し、自分のプロジェクトに合った直感を育てることが到達点です。

2-6. スキルの基本と最小構成

スキルは最も柔軟な指示の手段です。実体は SKILL.md という Markdown ファイル 1 枚。Claude が自動で読み込むことも、/名前 であなたが呼び出すこともできます。

  • ディレクトリに SKILL.md を置くだけで、Claude のツールキットに手順・知識が追加される
  • 本文は使用時にしか読み込まれないため、長い参照資料でも普段はほぼ無コスト
  • カスタムコマンド（.claude/commands/*.md）はスキルに統合済み。両者とも /deploy として動作するが、スキルの方が高機能（補助ファイル、呼び出し制御、自動発火）
  • Claude Code のスキルは Agent Skills オープン標準に準拠。他の AI ツールとも互換性がある

作成する目安：同じプレイブック・チェックリスト・複数ステップの手順を繰り返し貼り付けているとき、または CLAUDE.md の一節が「事実」ではなく「手順」に育ってきたとき。

最小構成

---
description: 未コミットの変更を要約し、危険な点にフラグを立てる。差分レビューやコミットメッセージを求められたときに使う。
---

## Current changes

!`git diff HEAD`

## Instructions

上記の変更を 2〜3 個の箇条書きで要約し、エラー処理の欠落・
ハードコードされた値・更新が必要なテストなどのリスクを列挙してください。
my-skill/
├── SKILL.md          # メイン指示（必須）
├── reference.md      # 詳細な API ドキュメント（必要時に読む）
├── examples/
│   └── sample.md
└── scripts/
    └── validate.sh   # Claude が実行できるスクリプト

SKILL.md は 500 行以下を目安に。詳細は補助ファイルへ逃がし、SKILL.md から参照させます。冒頭の --- で挟まれた部分がフロントマターで、次節で扱います。

置き場所と優先順位

場所パス適用範囲
Enterprise管理設定ディレクトリ組織内の全ユーザー
Personal~/.claude/skills/<name>/SKILL.md全プロジェクト
Project.claude/skills/<name>/SKILL.mdそのプロジェクトのみ
  • 同名なら enterprise > personal > project。バンドルスキルも同名の自作スキルで上書きできる
  • モノレポではネストした .claude/skills/ も検出され、/apps/web:deploy のような修飾名で呼び分けられる
  • ライブ変更検出：SKILL.md の追加・編集は再起動なしで反映される（~/.claude/skills/ を初めて作ったときだけ再起動が必要）
試してみる：30 秒でスキルを作る 
mkdir -p ~/.claude/skills/summarize-changes && cat > ~/.claude/skills/summarize-changes/SKILL.md <<'EOF'
---
description: 未コミットの変更を要約する。差分レビューを求められたときに使う。
---
!`git diff HEAD --stat`

上の変更を3行で要約し、気になる点を挙げてください。
EOF

git リポジトリ内で実行してください。セッションで /summarize-changes と打てば呼び出せます。後始末は rm -rf ~/.claude/skills/summarize-changes。

2-7. スキルのフロントマターと呼び出し制御

フィールド説明
description実質必須。Claude が「使うべきか」を判断する材料。主要ユースケースを先頭に書く

!`command` と書くと、スキル本文が Claude に渡る前にシェルコマンドが実行され、出力がその場に埋め込まれます。「Claude にコマンドを実行させる」のではなく、前処理でデータを差し込む仕組みです。複数行なら ```! で囲んだフェンスブロックを使います。組織で禁止したい場合は設定 disableSkillShellExecution: true（管理設定で強制可能）。

ライフサイクル

  • 呼び出されたスキルの本文は会話に 1 メッセージとして入り、セッション中ずっと残ります。単発の手順ではなく「常時適用される指示」として書くのが正解
  • 自動コンパクション時は、直近に呼び出されたスキルが予算内で再添付されます。効果が薄れたように見えるときはコンパクション後に再呼び出しします
  • 「発火したか」と「出力が期待通りか」は別問題。スキル有効／無効のベースライン比較で測るのが公式の推奨で、skill-creator プラグインがこのループを自動化します

2-8. 指示が効かないときの診断

順番が大事です。まず「読み込まれているか」を確かめてから、内容を疑ってください。読み込まれていないファイルをいくら書き直しても効きません。

  1. /context の Memory files を見る。ここに出ていなければ Claude は見ていない。中身を開いて直すのは /memory
  2. @ インポートが効かない場合、過去にインポートの承認ダイアログを拒否していないかを疑う（拒否は記憶され、再表示されない）
  3. 置き場所がセッションに読み込まれる階層かを確認（2-2 の読み込み順序）。サブディレクトリの CLAUDE.md と paths 付きルールは、該当ファイルに触れるまで読まれない
  4. セッションの途中で編集していないか確認する。プロジェクトルートの CLAUDE.md はセッション開始時に一度だけ読まれる（6-3）。反映は次の /clear か再起動から
  5. 指示をより具体的に書き換える／矛盾する指示を削除する
  6. 特定タイミングで必ず走らせたい処理はフックに移す（5-7）
  7. システムプロンプトレベルで必要なら --append-system-prompt（スクリプト向き）
  8. InstructionsLoaded フックで「いつ・なぜ・どのファイルが読まれたか」をログに取る（5-6）。設定全般の診断は /doctor /hooks

2-9. この章の持ち帰り

CLAUDE.md とスキルは最もコスパの高い投資ですが、効かせ方を外すと固定費だけが増えます。

覚えること仕事での効き目具体的な操作
永続化は文脈であって強制ではない「書いたのに守られない」を不具合ではなく仕様として予測できる。書く前に、伝える文脈と守らせる規則を分けられる禁止事項は PreToolUse フック or deny ルールへ（5 章）
実際に読まれたかは /context で確認読まれていないファイルをいくら書き直しても効かない。診断はここから始める/context の Memory files
200 行以下・検証可能な粒度で書く長いほど遵守率が下がる。「適切に」ではなく「インデントは 2 スペース」と書く/init でたたき台 → 削って育てる
同じ指摘を 2 回したら CLAUDE.md、同じ手順を 3 回貼ったらスキル書くタイミングの判断で迷わなくなる。スキルは呼ばれるまでコンテキストを食わない# でその場から追記／~/.claude/skills/<name>/SKILL.md
常時ロードを rules に逃がす該当ファイルを触ったときだけ読ませれば、毎リクエストの固定費が下がる.claude/rules/*.md に paths:
必ず検証手段を渡す「見張るセッション」と「任せられるセッション」を分ける最大の要因「まず失敗するテストを書いて、その後で修正して」
