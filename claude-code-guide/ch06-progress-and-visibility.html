06

進行状況の可視化

エージェントに任せる時間が長くなるほど、「今どこにいるのか」が見えないことが最大のストレスになります。Claude Code は、着手前の計画・実行中のチェックリスト・並列作業の進捗・資源の消費を、それぞれ別の仕組みで可視化します。

原理との対応

この章は図 1-1（1-1）の運用と観測性——ループとコンテキストを外から測る領域——と、3-9 メモリ の「分ける」の実装です。タスクリスト（6-2）・実行中セッションの確認（6-4）・ステータスライン（6-6）は、ループが今どの周回にいてコンテキストを何が占めているかを外から見る手段で、可視化自体がツール定義としてコンテキストを消費する（6-1）のは 3-9 ツール使用 の帰結です。動的ワークフロー（6-3）と並列手段の選び方（6-7）は、別のコンテキストで回して要約だけを元に戻す「分ける」操作を、規模と調整役の違いで並べたものです。/goal（6-5）の評価器が会話に出たものしか見ないのは、3-9 コンテキスト（コンテキストに無いものは知らない）がそのまま現れた例です。廃れないのは「計測はコンテキストとループに対して行う」「分離は要約だけを戻す」という構造で、変わるのはコマンド名・既定のオン／オフ・エージェント数の上限です。

6-1. 可視化の対象

「進捗を見たい」という要望は、実際には粒度の違う 4 つに分かれます。手段が違うので、まず自分がどれを求めているのかを決めます。

見たいものタイミング手段本章
これから何をするか着手前Plan Mode（Shift+Tab）、/ultraplan、ワークフローのプラン承認2-4 / 6-3
どこまで進んだか1 セッション内タスクリスト（TaskCreate 系）6-2
何が並行して動いているか実行中/tasks、/workflows、claude agents6-4
どれだけ資源を使ったか常時ステータスライン、/context、/usage6-6
可視化はコストでもある

チェックリストやワークフローの進捗表示は、ツール定義やリマインダとしてコンテキストを消費します。実際、後述するタスクツールが新しいモデルで既定オフになっているのはこの理由です。「常に全部を見えるようにする」ではなく、必要な粒度だけを選ぶのが正解です。

6-2. タスクリスト

多段の作業を「□ 完了 / ▶ 実行中 / □ 未着手」の形で追いたい——これを担うのがタスクツール（TaskCreate TaskGet TaskList TaskUpdate）です。

最初に知るべきこと：新しいモデルでは既定で無効

Claude Code v2.1.233 以降、Opus 4.8 / Sonnet 5 / Fable 5 / Mythos 5（および各系列の後継）ではこれらのツールが既定で提供されません。公式の理由は「これらのモデルは書き出さなくても多段の作業を追えるうえ、ツール定義とリマインダがコンテキストを占めるため」です。Opus 4.7 など他のモデルでは既定で提供されます。

結果として「チェックリストが出てこない」という状態になります。これは不具合ではなく既定の挙動です。Opus 4.7 など従来のモデルでは 4 つのタスクツールが既定で提供されます。

有効化する

試してみる：タスクリストを出す 
CLAUDE_CODE_ENABLE_TODO_TOOLS=1 claude    # 全モデル・全プロバイダで有効化claude --allowedTools TaskCreate          # ツール名を明示して有効化

ほかに --tools で列挙する方法もあります（セッションの組み込みツールをそこに挙げたものへ限定するので、他に使うツールも一緒に書く必要があります）。Agent SDK では allowedTools / tools オプションが同じように働きます。

例外と波及

  • バックグラウンドセッションと Claude Code on the web では、モデルによらず常に提供されます
  • サブエージェントは、親セッションが持っているときだけ持ちます（サブエージェントが別モデルで動いていても親に従う）
  • エージェントチームでは、タスクツールが無いとメンバーは共有タスクリストではなくメッセージで協調します。別ペインで動くメンバーは独立プロセスなので、自分のモデルの既定に従います
  • TodoWrite は TaskCreate 系に置き換えられた旧ツールです。従来モデルで使いたい場合は CLAUDE_CODE_ENABLE_TASKS=0 で戻せます

6-3. 動的ワークフロー

普段の Claude Code は、Claude が毎ターン「次に何をするか」を考えながら進みます。動的ワークフローは、その進め方をClaude が書いたスクリプトに置き換えます。

何が変わるのか — 2 点だけ

1
計画がコードになる

ループ・分岐・並列化をスクリプトが持つので、同じ手順を毎回まったく同じに再実行できる。保存すれば /<名前> で呼べる。

2
中間結果が会話に載らない

結果はスクリプト変数に留まる。コンテキストを溢れさせずに数十〜数百のエージェントを回せる。

使うとき／使わないとき

状況判断
同じ検査を大量の対象に繰り返す（全エンドポイントの認証漏れ監査、100 ファイルの一括移行）✅ 使う
1 つのコンテキストに収まらない規模の調査✅ 使う
同じ手順を今後も繰り返す（ブランチごとのレビューなど）✅ 使う（保存して再利用）
相互チェックさせたい（独立したエージェントに互いの所見をレビューさせる）✅ 使う
数ファイルの修正、1 つのバグ調査❌ 過剰。通常の会話かサブエージェントで足りる
途中で人が判断を挟みたい❌ 実行中は入力を挟めない。段階ごとに別ワークフローにする
試行錯誤しながら方針を決めたい❌ 先に Plan Mode で方針を固める

メリットとデメリット

メリットデメリット
コンテキストを消費せずに大規模並列ができるトークン消費は会話でやるより大きい（多数のエージェントを起動するため）
オーケストレーション自体を保存・配布・再実行できる実行中にユーザー入力を挟めない（止まるのは権限プロンプトのみ）
バックグラウンドで走るのでセッションは応答し続けるスクリプトはファイルやシェルに直接触れない。読み書きと実行はエージェント任せ
中断しても同一セッション内で再開できる同時 16 / 総計 1,000 エージェントの上限がある
スクリプトが書き出されるので、何をしたか検証できるエージェントはセッションのモデルを使う。大きな実行の前に /model の確認が要る
まず小さく試す

いきなりリポジトリ全体にかけず、1 ディレクトリや絞った問いで 1 回走らせ、/workflows でトークン消費を見てから広げてください。25 エージェント超または見込み 150 万トークン超で Large workflow の警告が出ます（助言であり実行は止まりません）。規模の目安は /config の Dynamic workflow size で調整できます。既定は medium（15 エージェント未満）で、small 5／large 50 エージェント未満、unrestricted は制限なし（v2.1.219 より前は unrestricted が既定。日本語版ドキュメントは旧記述のままです）。

他の並列手段との違い

サブエージェントエージェントチームワークフロー
計画を持つのはClaude（ターンごと）リードエージェント（ターンごと）スクリプト
中間結果の置き場Claude のコンテキスト共有タスクリストスクリプト変数
再利用できるもの作業者の定義チームの定義オーケストレーション自体

使い方

試してみる：ワークフローを走らせる 
ultracode: src/routes/ 配下の全 API エンドポイントを認証チェック漏れで監査して/workflows    # 実行中・完了済みの一覧 → 選ぶと進捗ビュー
  • プロンプトに ultracode を含めるか「ワークフローで」と頼めば、その 1 タスクだけワークフローになる
  • /effort ultracode にすると、以降セッション中の実質的な作業すべてにワークフローを組む
  • キーワードが効くのは自分でタイプしたプロンプトだけ。-p、スケジュールタスク、Webhook 経由では発火しない
  • 誤って発火したら Option+W（macOS）／Alt+W（Windows・Linux）で解除

6-5. ゴール駆動で走らせ続ける — /goal

「テストが全部通るまで」のような完了条件を宣言すると、毎ターン後に別モデルの評価器が条件の充足を判定し、満たすまで作業を続けます。

試してみる：完了条件を決めて任せる 
/goal test/auth のテストが全て通り、lint も通る/goal          # 現在の状態と、直近の評価理由を確認/goal clear    # 解除

セッションを走らせ続ける 3 つの方法

方法次のターンが始まる契機止まるとき
/goal前のターンが終わったとき評価器が条件充足または達成不能と判断、修正が必要なエラーで失敗、/goal clear
/loop一定時間が経過したとき自分で止める、または Claude が完了と判断
Stop フック前のターンが終わったとき自分のスクリプトかプロンプトが決める

/goal はセッション限定の手軽な手段、Stop フックは設定ファイルに置いてそのスコープの全セッションに効かせる手段です。決定的な検査ならスクリプト、モデル判断ならプロンプトで書けます。

効く条件の書き方

評価器は会話に出たものしか見ない

評価器はコマンドを実行せず、ファイルも独自には読みません。判断材料は Claude が会話に出した内容だけです。したがって条件は「Claude 自身の出力で示せるもの」として書く必要があります。「test/auth のテストが全て通る」が成立するのは、Claude がテストを実行して結果がトランスクリプトに載るからです。

  • 測定可能な終了状態を 1 つにする：テスト結果、ビルドの終了コード、ファイル数、キューが空
  • ゴールは権限モードを変えません。無人で回したいなら auto mode と組み合わせます。auto mode はツール単位の確認を消し、/goal はターン単位の確認を消すので、両者は補完関係です
  • アクティブな間は ◎ /goal active の表示が出て、経過時間が分かります。Ctrl+O のトランスクリプトビューアで評価理由を読めます
  • バックグラウンド作業がゴールを待たせている間は、アイドルでも評価ターンが発生しえます（7-7のコスト要因のひとつ）

6-6. ステータスライン

/context や /usage は「見に行く」ものですが、ステータスラインは常に見えている点が違います。コンテキスト残量やキャッシュの温度を横目で把握できると、/clear や /compact の判断が早くなります。

試してみる：自然言語で作らせる 
/statusline モデル名とコンテキスト使用率をプログレスバー付きで表示して

スクリプトが ~/.claude/ に生成され、設定も自動で更新されます。手で書く場合は設定の statusLine にコマンドを指定します。

スクリプトが受け取れる主なデータ

フィールド中身注意
context_window.used_percentageコンテキスト使用率入力トークンだけから算出（出力は含まない）
current_usage入力・出力・キャッシュ書き込み・キャッシュ読み出しの内訳最初の API 呼び出し前と /compact 直後は null
prompt_cachehit_ratio / warm / ttl / misses短い表示なら warm と hit_ratio の 2 つで足りる（7-3）。v2.1.251 以降で、最初の API 応答までは存在しない
その他git の状態、モデル名、レート制限、セッションのコストと経過時間—

6-7. 並列作業の選び方

並列化の手段は 4 つあります。公式が示す選択軸は3 つの問いです。

問い 1 — 誰が作業を調整するのか

調整するのは使うもの本資料
Claude が 1 つの会話の中で委譲し、結果を回収するサブエージェント11 章
自分が独立したタスクを渡し、後で見に行くエージェントビュー6-4

問い 3 — 同じファイルを触るか

触るなら worktree で隔離します。サブエージェントと自分で起動したセッションは、それぞれ別の worktree を使えます。エージェントチームはメンバーを worktree で隔離しないので、メンバーごとに担当ファイルを分ける形で作業を分割してください。

worktree はキャッシュも分ける

プロンプトキャッシュは実質的にディレクトリ単位です。worktree はディレクトリが別なので、互いのキャッシュを読みません（7-3）。隔離の代償として、それぞれが自分のキャッシュを温め直します。

6-8. この章の持ち帰り

「今どこにいるか分からない」は、見たい粒度に応じて別々の道具で解きます。
