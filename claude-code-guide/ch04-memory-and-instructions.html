04

記憶と指示

セッションをまたいで知識を保持する仕組みは 2 系統あります。あなたが書く CLAUDE.md と、 Claude が自分で書く自動メモリです。どちらも「強制設定」ではなく「コンテキスト」である点が肝心です。

原理との対応

この章は 図 1-1 の長期メモリの実装で、根拠は 3-9 メモリ の 4 操作のうち「外に残す」（永続化）です。人が書く CLAUDE.md・rules と、モデルが書く自動メモリの 2 系統は、どちらも次のセッションのコンテキストの先頭に読み込まれる（3-9 コンテキスト）だけで、モデルへの強制力はありません。だから 4-6 の診断は「読み込まれているか」から始まり、絶対に守らせたいことはハーネス側（フック・deny ルール。3-9 ガードレール）へ逃がします。廃れないのは「永続化は文脈であって強制ではない」「起動時に読んだ分は毎ターンの固定費」の 2 点で、置き場所のパス・読み込み順・200 行や 25KB といった上限は変わります。

4-1. 2 系統の記憶

CLAUDE.md自動メモリ
誰が書くかあなたClaude
内容指示・ルール学習・パターン
スコーププロジェクト／ユーザー／組織リポジトリ単位（worktree 間で共有）
読み込み毎セッション（全文）毎セッション（MEMORY.md の先頭 200 行 / 25KB）
保存場所下表参照~/.claude/projects/<project>/memory/
原則

どちらも Claude に読ませるコンテキストであり、遵守は保証されません。「絶対に守らせたい」ことは PreToolUse フックか権限の deny ルールで強制してください。

4-2. CLAUDE.md の置き場所とスコープ

スコープ場所目的共有範囲
管理ポリシーmacOS: /Library/Application Support/ClaudeCode/CLAUDE.md
Linux/WSL: /etc/claude-code/CLAUDE.md
Windows: C:\Program Files\ClaudeCode\CLAUDE.md		組織全体の指示（IT 配布）組織の全ユーザー（除外不可）
ユーザー指示~/.claude/CLAUDE.md個人の好み自分（全プロジェクト）
プロジェクト指示./CLAUDE.md または ./.claude/CLAUDE.mdチーム共有の規約リポジトリの全員
ローカル指示./CLAUDE.local.md（.gitignore 推奨）個人的なプロジェクト設定自分のみ

読み込み順序

  • @path/to/file 構文で他ファイルをインポート可能（最大 4 ホップ。インポート先も起動時に展開される）。プロジェクト側のファイルから作業ディレクトリ外を初めてインポートすると承認ダイアログが出ます。拒否するとインポートは無効のままになり、ダイアログは二度と表示されません（「インポートが効かない」の典型的な原因）。~/.claude/CLAUDE.md や ~/.claude/rules/ は自分で書いたものなので、ダイアログなしで読み込まれます
  • モノレポで無関係な CLAUDE.md を除外したい場合は設定の claudeMdExcludes を使う
AGENTS.md がある場合

Claude Code が読むのは CLAUDE.md のみです。既に AGENTS.md がある場合は CLAUDE.md に @AGENTS.md と書いてインポートするか、シンボリックリンクを張ります。

試してみる：読み込まれている指示を確認 
/context   # 実際に読み込まれたものを「Memory files」で確認/memory    # 置き場所の一覧。その場で開いて編集できる

/memory が出すのは置き場所の一覧で、まだ存在しないファイルの枠も並びます（実測）。今のセッションに実際に読み込まれたかは /context の Memory files で確認してください。

4-3. CLAUDE.md の書き方

原則具体的にどうする例
サイズ1 ファイル 200 行以下を目標長いほどコンテキストを食い、遵守率が下がる
構造Markdown 見出しと箇条書きでグルーピングClaude も人間と同じように構造をスキャンする
具体性検証可能な粒度で書く×「コードを適切にフォーマットする」→ ○「インデントは 2 スペース」
×「変更をテストする」→ ○「コミット前に npm test を実行」
×「ファイルを整理する」→ ○「API ハンドラは src/api/handlers/ に置く」
一貫性定期的に棚卸しする矛盾するルールがあると Claude は任意に一方を選ぶ
書くタイミングサインが出たら追記する同じ間違いを 2 回された／同じ説明を 2 回打った／レビューで同じ指摘が出た
 
# Code style
- ES modules（import/export）を使う。CommonJS は使わない
- 可能な限り分割代入で import する

# Workflow
- 変更後は必ず `npm run typecheck` を実行
- パフォーマンス上、テストは単一ファイル単位で実行する

/init でひな形を自動生成できます（既存があれば改善提案）。/doctor は肥大化した CLAUDE.md のトリム候補も提示します。

試してみる：最小の CLAUDE.md を置く 
# 既存の CLAUDE.md を消さないよう追記する（> ではなく >>）
cat >> CLAUDE.md <<'EOF'

# Workflow
- 変更後は `npm test` を実行する
- コミット前に `npm run lint` を通す
EOF

コマンドは自分のプロジェクトのものに置き換えてください。/init で生成済みの内容を消さないよう、>> で追記しています。

4-4. .claude/rules/ によるパス限定ルール

CLAUDE.md が膨らんできたら、トピック別ファイルに分割します。paths を指定すると一致するファイルを触ったときだけ読み込まれ、コンテキストを節約できます。

your-project/
└── .claude/
    ├── CLAUDE.md            # 常時読み込まれるコア規約
    └── rules/
        ├── code-style.md
        ├── testing.md
        └── api-design.md    # paths 指定で条件付き読み込み
---
paths:
  - "src/api/**/*.ts"
  - "lib/**/*.{ts,tsx}"
---

# API 開発ルール
- すべてのエンドポイントに入力検証を入れる
- 標準のエラーレスポンス形式を使う
  • paths なしのルールは .claude/CLAUDE.md と同じ優先度で起動時に読み込まれる
  • .md は再帰的に検出されるので rules/frontend/ のような整理も可能
  • シンボリックリンク対応。複数リポジトリで共通ルールセットを共有できる
  • ユーザーレベルは ~/.claude/rules/（プロジェクトルールより先に読み込まれる＝プロジェクト側が優先）
試してみる：パス限定ルールを作る 
mkdir -p .claude/rules && cat > .claude/rules/testing.md <<'EOF'
---
paths: ["**/*.test.ts"]
---
- テストは Arrange-Act-Assert の順で書く
EOF

次に *.test.ts を触らせると、このルールだけが追加で読み込まれます。

4-5. 自動メモリ（auto memory）

項目内容
何が保存されるか4 種類（フロントマターの type）。user＝あなたの役割・専門・作業の好み／feedback＝あなたの指摘と、確定した進め方／project＝進行中の作業・期限・コードや git 履歴から導けない決定／reference＝Issue トラッカー等、プロジェクト外の情報の在り処
保存されないものコードベースから導けること（アーキテクチャ、ファイルパス、デバッグの修正内容）と、CLAUDE.md に既に書いてあること。毎セッション必ず保存するわけでもない
既定と無効化既定で有効。/memory のトグル、autoMemoryEnabled: false、CLAUDE_CODE_DISABLE_AUTO_MEMORY=1
保存場所と構成~/.claude/projects/<project>/memory/。MEMORY.md がインデックスで、詳細は個別トピックファイルに分離される
起動時に読まれる範囲MEMORY.md の冒頭のみ（上限は 4-1）。トピックファイルはオンデマンド
閲覧・編集・共有すべてプレーンな Markdown。/memory から閲覧・編集・削除できる。マシンローカルで他マシンとは共有されない
サブエージェントmemory: フィールドで独自の永続メモリを持たせられる
使い分け

「今後は npm ではなく pnpm を使って」と会話で頼むと自動メモリに保存されます。チームで共有すべきルールは自動メモリではなく CLAUDE.md に明示的に書いてください（自動メモリはコミットされません）。

試してみる：自動メモリに書かせて確認する 
このプロジェクトのテストは npm test で走ることを覚えておいて/memory

保存先は ~/.claude/projects/<project>/memory/ で、/memory から中身を確認できます。

4-6. 指示が効かないときの診断

順番が大事です。まず「読み込まれているか」を確かめてから、内容を疑ってください。読み込まれていないファイルをいくら書き直しても効きません。

  1. /context の Memory files を見る。ここに出ていなければ Claude は見ていない。中身を開いて直すのは /memory（こちらは置き場所の一覧なので、未作成のファイルも並ぶ）
  2. @ インポートが効かない場合、過去にインポートの承認ダイアログを拒否していないかを疑う（拒否は記憶され、再表示されない）
  3. 置き場所がセッションに読み込まれる階層かを確認（4-2 の読み込み順序）
  4. 指示をより具体的に書き換える／矛盾する指示を削除する
  5. 特定タイミングで必ず走らせたい処理は hook に移す
  6. システムプロンプトレベルで必要なら --append-system-prompt（スクリプト向き）
  7. InstructionsLoaded フックで「いつ・なぜ・どのファイルが読まれたか」をログに取る（12-2）
  8. 設定全般の診断は /doctor /hooks /mcp

4-7. この章の持ち帰り

CLAUDE.md は最もコスパの高い投資ですが、効かせ方を外すと固定費だけが増えます。

覚えること仕事での効き目具体的な操作
永続化は文脈であって強制ではない「書いたのに守られない」を不具合ではなく仕様として予測できる。書く前に、伝える文脈と守らせる規則を分けられる3-9 メモリ・3-9 ガードレール
実際に読まれたかは /context で確認読まれていないファイルをいくら書き直しても効かない。診断はここから始める/context の Memory files
200 行以下・検証可能な粒度で書く長いほど遵守率が下がる。「適切に」ではなく「インデントは 2 スペース」と書く/init でたたき台 → 削って育てる
同じ指摘を 2 回したら追記する書くタイミングの判断で迷わなくなる。レビューの手戻りが目に見えて減る# でその場からメモリに追記
常時ロードを rules に逃がす該当ファイルを触ったときだけ読ませれば、毎リクエストの固定費が下がる.claude/rules/*.md に paths:
絶対に守らせたいことは指示にしないCLAUDE.md は「お願い」。禁止事項は強制できる層に置くPreToolUse フック or deny ルール
意外と知られていない

@ インポートの承認ダイアログを一度でも拒否すると、インポートは無効のままになり、ダイアログは二度と表示されません。「インポートが効かない」の典型的な原因です。もう一つ、プロジェクトルートの CLAUDE.md はセッション開始時に一度だけ読まれるため、作業中に編集しても、そのセッションには反映されません（7-3）。反映は次の /clear か再起動からです。
