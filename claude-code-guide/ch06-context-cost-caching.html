06

コンテキスト管理・コスト・プロンプトキャッシュ

トークンは有限で有料です。この章は仕組み → 測る → 減らす → 異常時の順に並べています。「速く動かす」ことと「安く動かす」ことは、多くの場合同じ施策、コンテキスト管理に帰着します。

原理との対応

この章は図 1-1 のコンテキストウィンドウと、それを外から測る運用と観測性の実装です。根拠は 3-6 コンテキスト（有限で、毎ターン丸ごと送る。先頭一致でキャッシュされる。出力は入力より高い）と 3-6 メモリ の「縮める」「捨てる」です。廃れないのは「短く保つ」「先頭を固定する」「出力（推論を含む）を無駄に増やさない」の 3 つが効くという構造で、変わるのはウィンドウ幅・単価・プランの倍率・キャッシュの寿命・トークナイザの数値です。

6-1. コンテキストウィンドウ

コンテキストウィンドウ（context window）には、会話履歴・ファイル内容・コマンド出力・CLAUDE.md・自動メモリ・読み込まれたスキル・システム指示が同居します。ここが Claude Code 運用の最大の制約です。

英語は 3.5 文字/トークン、日本語は約 1.2 文字/トークン（類推）で換算した概算です。実際にはシステムプロンプトと CLAUDE.md などの固定分が先に数万トークンを占め、読んだファイルとツール出力が以降ずっと残ります。200K でも「2 万行を読ませられる」わけではありません。

いつ何が読み込まれるか

すべてが起動時に読まれるわけではありません。起動時に読まれるものだけが、毎リクエストの固定コストになります。

6-2. 何がトークンを消費するのか

モデルはリクエスト間で何も記憶しません。ツールを使うたびに新しいリクエストが飛び、そのつど「開始時に読んだ固定分＋それまでの履歴」を丸ごと運びます。

積算の内訳

要素いつ乗るか効かせ方
システムプロンプト＋組み込みツールの定義固定分通常はキャッシュ読み。削るとキャッシュも切れる
CLAUDE.md・自動メモリ・スコープ無しの rules固定分短く保つ。資料はスキルへ（2-1）
スキルの説明文固定分説明文は 1 行に。自分だけが叩くスキルは disable-model-invocation: true で説明文すら乗らなくなる
読み込んだファイル／ツール実行結果読んだ以降ずっと読ませすぎない。フックで前処理して絞る（6-6）
拡張思考の思考トークン有効なターン出力トークンとして課金。努力レベルを作業に合わせる（3-3）
コンパクション/compact・自動圧縮のたび要約の生成が出力コスト。タスクの切れ目に自分で実行する
やり直し・手戻り方向を間違えたとき最大の変動費。プランモードと早期の軌道修正（2-5）
コンパクションは「リセット」ではない

会話は要約に縮みますが固定分は残ります。CLAUDE.md と自動メモリはディスクから再注入され、呼び出し済みのスキル本文も予算内（1 スキル 5,000・合計 25,000 トークン）で再添付されます。ゼロから始めたいなら /clear です。

6-3. プロンプトキャッシュ（prompt caching）

キャッシュを壊す操作をタスクの途中で行うと、そのターンだけ約 10 倍の入力コストを払います。総消費を左右する最大の変数です。

3 層のプレフィックス一致

API はリクエストの先頭（プレフィックス）を直前の処理内容と照合します。前方に 1 箇所でも変化があると、それ以降は全て再計算されます。

層内容変わるとき
システムプロンプト中核の指示、ツール定義、出力スタイルロードされるツール定義が変わる、Claude Code がアップグレードされる
プロジェクトコンテキストCLAUDE.md、自動メモリ、スコープ無しの rulesセッション開始、/clear、/compact の後
会話発言、応答、ツール結果毎ターン

加えて、プロンプト本文ではないのにキャッシュキーに含まれるものが 2 つ、モデルと努力レベルです。

キャッシュを壊す操作／保つ操作

壊す
タスクの途中では避ける

モデル切替（/model）／努力レベル変更（/effort）／高速モードの有効化（/fast）／ツール全体の deny 追加／/compact／Claude Code のアップグレード

保つ
いつ行ってもよい

リポジトリのファイル編集／CLAUDE.md の編集／出力スタイルの変更／権限モードの変更／スキルの呼び出し／/recap／/rewind

「保つ」側の副作用

キャッシュを保つことは、その変更がセッション中は適用されないことと表裏です。プロジェクトルートの CLAUDE.md と出力スタイルはセッション開始時に一度だけ読まれるため、途中で編集しても効きません（反映は次の /clear か再起動から）。「CLAUDE.md を直したのに従わない」の正体はこれです（2-8）。ネストした CLAUDE.md と paths: 付き rules は後から読まれるため、ロード前の編集は反映されます。

高速モードは会話の途中でオンにすると高い

会話中に初めて有効化すると、その時点のコンテキスト全体を高速モードの未キャッシュ単価で払い直します。深いところで入れるほど高くつくため、使うならセッションの最初から。この課金は 1 会話につき 1 回で、後からオフ・オンを繰り返しても再発しません。

キャッシュの寿命（TTL）

リクエストの種別サブスクリプション（プラン内）使用量クレジット／API キー／クラウドプロバイダ
メイン会話（対話ターン、-p）1 時間5 分
それ以外（コンパクション等のヘルパー）5 分（一部は 1 時間）5 分
  • プラン上限を超えて使用量クレジットに入ると、メイン会話も 5 分に落ちます。「上限を超えた後に急に高くつく」と感じる一因がこれです
  • promptCacheTtl 設定または CLAUDE_CODE_PROMPT_CACHE_TTL 環境変数に 1h を指定すれば 1 時間を維持できます（v2.1.242 以降）
  • キャッシュは実質的にマシンとディレクトリ単位。別ディレクトリのセッションは互いのキャッシュを読みません（worktree も別扱い。4-3）。同じディレクトリの並行セッション同士は共有します

運用の原則

  1. モデル・努力レベル・高速モードはセッション冒頭で決める。途中で変えない
  2. /compact はタスクの切れ目で自分から実行する。自動圧縮がタスクの最中に走るより安い
  3. 継続が不要なら /compact ではなく /clear。/clear は要約を生成しないぶん実質コスト 0
  4. 長い中断の後に古いセッションを --resume すると、キャッシュが切れているため最初の 1 ターンが最も高くつく（4-1）

Claude Code は有料プランに含まれます。無料プランでは使えません。表は上ほど規模が大きく高額です。

使用量は5 時間ごとのウィンドウと週次でリセットされ、Claude チャットとも共有されます。上限を超えても止めたくない場合は使用量クレジット（usage credits）を有効にすると、超過分が従量課金で継続されます（ただしキャッシュの寿命が 5 分に落ちる。6-3）。

API・クラウドプロバイダ（従量課金）

経路課金向いている使い方
Claude Console（API キー）トークン従量課金（6-2 の単価表）。ワークスペース単位で支出制限スクリプト・自動化、シート課金が合わない使い方
Amazon Bedrock / Google Cloud / Microsoft Foundry既存のクラウド契約に従量課金。予算管理はクラウド側データを既存のクラウド境界内に収めたい組織

ローカルで動くもの（CLI・フック・スキル・チェックポイント）はどの経路でも使えます。差が出るのは claude.ai と連携する機能（Web 版・モバイル・デスクトップアプリ・Remote Control など）で、これらはサブスクリプションのみです。プランごとの機能差は変更が入るため、調達前に機能の可用性で最新を確認してください。

見積もりの目安

公式の注意として、コーディング用のシートはチャット用より多く予算を見込むこと。1 回のデバッグセッションがチャット 1 日分以上を消費しうるためです。どの経路でも変わらないのは、支払っているのが「毎ターン丸ごと送るコンテキストの長さ」と「出力の量」だという点です。

言語ごとのトークン量

同じ内容でも、書く言語によってトークン数は変わります。英語の散文は公式の目安で 1 トークン ≒ 3.5 文字、コードは記号・インデント・改行がそれぞれトークンを消費するため散文より約 3 割効率が悪くなります。

この図は参考値。固定の定数として扱わない

cl100k_base は OpenAI のトークナイザで、Claude のものではありません。比はモデル更新でも動きます（Claude 4.7 以降は新しいトークナイザで、同じテキストで約 30% 多くのトークンを生成すると公式が注記しています）。中国語と英語のプロンプトを比較した研究では、非英語で書いてもトークンは減らず、解決率も下がる傾向でした（類推）。

ただし問題は量ではなく頻度です。会話は毎リクエストで全履歴が再送されるため、常時読み込まれる CLAUDE.md・スコープ無しの rules・スキルの description だけが固定費として毎ターン乗り続けます。呼び出したときだけ読まれるスキル本文や参照資料は日本語で書いてかまいません。結論は「指示は短く、資料はオンデマンドに」。日本語で書くこと自体を避ける必要はなく、避けるべきは常時ロードされる場所に長文を置くことです。

実際に測ってみる — 自分の固定費と、言語による差

API キーは不要です。計測のときは --safe-mode（CLAUDE.md・自動メモリ・スキル・フックなどほぼ全部を無効化）で素の状態を基準にし、DISABLE_PROMPT_CACHING=1 を付けます。付けないと入力の大半がキャッシュに回り、input_tokens が実態を映しません。そのぶん毎回全文が未キャッシュで処理されるので、確認したいときだけ実行してください。

手順 1：自分の CLAUDE.md がいくら掛かっているか

同じプロンプトを、設定ありとなしで測って引き算します。毎リクエスト乗る固定費がそのまま出ます。

usage() { python3 -c 'import json,sys; print("in", json.load(sys.stdin)["usage"]["input_tokens"])'; }

printf '通常          : '; echo ok | DISABLE_PROMPT_CACHING=1 claude -p --output-format json --max-turns 1 | usage
printf 'CLAUDE.md なし: '; echo ok | CLAUDE_CODE_DISABLE_CLAUDE_MDS=1 DISABLE_PROMPT_CACHING=1 claude -p --output-format json --max-turns 1 | usage
printf 'safe-mode     : '; echo ok | DISABLE_PROMPT_CACHING=1 claude -p --safe-mode --output-format json --max-turns 1 | usage

出力例（ある環境での一例・実測。数値は人によって大きく違います）：

通常          : in 40488
CLAUDE.md なし: in 23420   ← CLAUDE.md・rules・自動メモリで 17,068
safe-mode     : in 16134   ← さらにスキル・MCP などで 7,286

この例では CLAUDE.md 系だけで 17,000 トークン超が毎リクエストに乗っていました。ここが大きいなら、言語を英語に寄せるよりまず量を削るほうが効きます。内訳は /context で分類別に確認できます。

手順 2：言語による差を測る

小さな作業を英語と日本語でやらせ、入力・思考・出力のトークンをそれぞれ測ります。オフバイワンのバグを直させる作業で、考えて、説明して、コードを書く、という実際の使い方に近く、かつ数百トークンで終わります。

mkdir -p /tmp/tok && cd /tmp/tok && cat > task_en.txt <<'EOF'
Answer in English. Do not use any tools.

def last_n(items, n):
    return items[len(items) - n - 1:]

This should return the last n elements, but it returns n+1 elements.
Explain the bug in two or three sentences and show the corrected function.
EOF
cat > task_ja.txt <<'EOF'
日本語で答えてください。ツールは使わないでください。

def last_n(items, n):
    return items[len(items) - n - 1:]

これは末尾 n 件を返すはずですが、n+1 件返します。
バグの原因を 2〜3 文で説明し、修正版の関数を示してください。
EOF
measure() {
  DISABLE_PROMPT_CACHING=1 claude -p --safe-mode --model haiku --output-format json --max-turns 1 \
  | python3 -c 'import json,sys; u=json.load(sys.stdin)["usage"]; print("in",u["input_tokens"],"out",u["output_tokens"],"think",u["output_tokens_details"]["thinking_tokens"])'
}

printf 'base: '; echo ok | measure
printf 'en:   '; measure < task_en.txt
printf 'ja:   '; measure < task_ja.txt

出力例（Haiku 4.5・答え合わせ用の一例・実測）。base はシステムプロンプトなどの固定分で、入力はこれを引くとプロンプト本体のトークン数が出ます。

base: in 16101 out 128 think 108
en:   in 16170 out 588 think 425
ja:   in 16200 out 680 think 469

                  英語   日本語     比
入力（プロンプト）    69     99    1.43 倍
思考                425    469    1.10 倍
出力の合計          588    680    1.16 倍

この例で最も大きいのは思考トークンで、出力全体の約 7 割を占めています。プロンプト本体の差（1.43 倍）がそのまま総額に効くわけではない、というのがテキストを読ませるだけの計測では見えない点です。1 つの小さな作業を 1 回測っただけの例なので、判断に使う数値は自分がよく出すプロンプトで、同じディレクトリ・同じモデルで 3 回ほど測って均してください（思考と出力は同じプロンプトでもばらつきます）。

6-6. 使用量の削減とコンテキスト管理

効果の大きい順に 5 系統。上 2 つが金額への効き目が大きく、下にいくほど地道な削減です。

6-7. 想定より多いときの診断

何時間も開いたままのセッションは、体感の作業量に比べてプラン上限を大きく消費します。「席を外していたのに減っている」には、はっきりした原因があります。

原因何が起きているか対処
長いコンテキスト毎リクエストで全会話を送るタスクの切れ目で /clear。調査の範囲を絞る
キャッシュミスキャッシュ寿命を超える中断の後、最初の 1 通が全コンテキストを再処理する長い中断の前に /clear。再開は要約から
バックグラウンド処理裏に回った長いコマンドや /loop がアイドル中も動く/tasks で止める（4-4）
コンパクション要約の生成に出力トークンを使い、直後に会話キャッシュを作り直す継続が不要なら /clear
高速モード・高い努力レベル入力・出力とも単価が上がり、思考トークンが増える単純作業では下げる。ただし途中では変えず、次のセッションから
原因の特定は /usage が早い

Pro / Max / Team / Enterprise では、/usage が直近の使用量の 10% 以上を占める挙動に自動でフラグを立て、対処のヒントを添えます。上の表を上から疑うより先に見てください。

6-8. この章の持ち帰り

コスト削減は精神論ではありません。効き目の順に 3 つやれば大半が片づきます。

覚えること仕事での効き目具体的な操作
コンテキストは有限で、毎ターン丸ごと送る。コストはその長さ × 往復回数 ＋ 出力単価やプランが改定されても、「短く保つ」「先頭を固定する」「出力を増やさない」の 3 つが効くことは変わらない。新しい課金項目も、固定分・積み上がり・出力のどれかに位置づけられる3-6 コンテキスト
モデル・努力レベル・高速モードは冒頭で固定途中で変えるとキャッシュが壊れ、そのターンだけ入力が約 10 倍になる/model /effort は作業開始前に
継続不要なら /compact ではなく /clear/clear は要約を生成しないぶん実質コスト 0。惰性で /compact を打たない戻る予定があるなら先に /rename
キャッシュ読みは入力の 1/10、出力は入力の 5 倍「キャッシュに乗せる」「出力（思考を含む）を無駄に増やさない」の 2 点に集約できる単純作業に Opus と高い /effort を使わない
原因調査は /usage が最速直近の 10% 以上を占める挙動に自動でフラグが立つ。表を上から疑うより速い/usage（d / w で期間切替）
自分の固定費を一度測る毎リクエストに乗る CLAUDE.md・スキルの総量が分かる。削る優先度が決まるCLAUDE_CODE_DISABLE_CLAUDE_MDS=1 との差分
指示は短く、資料はオンデマンドに日本語で書くこと自体は問題ではない。常時ロードされる場所に長文を置くのが問題参照資料は CLAUDE.md からスキルへ
意外と知られていない

高速モードを会話の途中で有効にすると、その時点のコンテキスト全体を未キャッシュ単価で払い直します。深いところで入れるほど高くつくので、使うならセッションの最初からです（課金は 1 会話につき 1 回）。もう一つ、プロンプトキャッシュは実質的にディレクトリ単位で、worktree は別扱いのため互いのキャッシュを読みません。並列化の隠れたコストです。
